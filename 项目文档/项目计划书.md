项目计划书

状态：当前业务需求基线；实现与验收进度见功能开发清单和开发进度审核报告
文档日期：2026 年 9 月 11 日  
项目性质：本科毕业设计，Web 管理系统  
开发方式：个人独立开发，以 AI coding 辅助实现，由开发者审核、验证和集成  
技术基线：Vue 3 前端与 Spring Boot／MySQL 单体后端；详细技术及工程约束分别由架构文档和开发规范维护。UI 基线已确认，统一 token、布局与交互约束见[前端 UI 设计与规范](前端UI设计与规范.md)。

## 一、项目概述

本项目拟建设一套面向高校社团、学生组织等小型组织的活动管理系统。系统以活动为主线，将组织成员、立项审批、任务协作、报名、经费记录、物资准备、反馈总结和资料归档关联起来，让负责人能够从一场活动中查看相关信息和处理结果。

本项目中的“全生命周期”指活动从构思、立项、筹备、执行到复盘归档的管理过程。执行阶段通过任务状态、执行记录和异常说明体现；系统不承担现场身份核验或考勤，不把报名记录解释为实际到场记录。

AI 仅提供两个简单亮点：**活动总结生成、活动方案生成**。两者都生成可编辑的文字草稿，由用户确认保存；不自动审批、不直接创建任务、不修改预算或成员权限。普通业务和人工编写功能不依赖模型服务可用性。

本文件是功能范围、业务边界和验收要求的唯一依据。历史材料不参与当前开发上下文；功能拆分见[功能开发清单](功能开发清单.md)。本计划不设置开发周期、工时估算或日期排期。

## 二、项目背景与目标

### 2.1 业务问题

项目关注以下问题：活动方案、任务、报名名单和支出分别保存在不同位置，负责人需要重复汇总；活动变更缺少统一记录；组织换届或负责人交接后，历史材料难以继续使用；活动总结和初步方案需要反复整理文字。

这些是本项目的需求假设，不作为已经完成用户调研的结论。后续使用实际活动表单和试用反馈检验设计，不预先宣称现有工具均无法解决，也不承诺未经测量的效率提升比例。

### 2.2 建设目标

1. **贯通活动管理。** 在同一活动下完成方案、立项、筹备、执行记录、反馈、总结和归档，关联任务、报名、经费及附件。
2. **明确多组织边界。** 同一账号可以加入多个组织；不同组织的内部数据相互隔离，活动负责人仅获得负责活动的管理权限。
3. **减少重复统计。** 基础工作台由实际业务记录计算，所有指标有统一口径，能够追溯到明细。
4. **保留两项可控 AI 辅助。** 总结和方案生成真实可调用、可修改、可确认，模型失败时用户可以继续手工操作。
5. **形成可验证成果。** 交付源代码、数据设计、业务与权限说明、测试记录、部署说明和演示数据。

### 2.3 服务对象与产品形态

| 项目 | 本版定义 |
| --- | --- |
| 主要场景 | 高校社团、学生组织开展讲座、展示、交流、公益等活动 |
| 组织范围 | 以约 50～500 人的小型组织为需求背景，不将人数直接视为并发或性能承诺 |
| 多组织含义 | 多个组织共享一套系统，各自管理成员与活动；不建设跨组织联合主办和跨行业流程配置 |
| 使用终端 | 同一 Web 系统通过响应式布局适配电脑和手机浏览器；管理页面优先适配电脑，公开活动浏览、登录、报名、结果查询、取消和反馈支持手机浏览器；不另行开发 App 或微信小程序 |
| 参与身份 | 组织内部成员及公开活动的外部报名者；外部报名不自动产生组织成员身份 |
| 应用边界 | 活动协作与记录工具，不作为现场考勤、支付结算或正式财务核算系统 |

## 三、首期开发范围

### 3.1 统一交付清单

下表中的功能均属于本版交付范围。“业务功能”与“AI 亮点”区分用途，不代表其中一类可以在验收时省略。基础归档、真实统计和两项 AI 功能不再与增强功能混列。

配套[系统功能图](../图示成果/项目ER图.html)按“系统—功能分组—模块—子功能”展示下列范围，可在同一页面切换 ER 图；[SVG 版本](../图示成果/系统功能图.svg)可用于文档排版。图中的四个功能分组仅用于展示，模块编号与下表一致。

| 编号 | 模块 | 本版交付内容 | 边界 |
| --- | --- | --- | --- |
| M01 | 账号、组织与成员 | 登录退出、账号身份、组织创建与切换、成员邀请与退出、负责人移交 | 固定身份与权限，不建设通用角色编辑器 |
| M02 | 活动管理 | 活动方案、基础信息、单级立项确认、驳回修改、筹备、执行记录、复盘、取消和归档 | 活动主状态与报名状态分开 |
| M03 | 任务协作 | 活动任务、负责人、截止时间、优先级、状态、说明及附件关联 | 不做子任务树、任务依赖、工时系统和逐任务审批 |
| M04 | 活动报名 | 内部或公开活动、固定报名字段、名额、人工审核、取消、本人报名记录和管理名单 | 不做签到、核验凭证和候补自动递补 |
| M05 | 经费记录 | 活动预算、支出登记、凭证附件、审核确认、驳回与作废、预算统计 | 不涉及付款、报销结算或组织资金账户 |
| M06 | 物资准备 | 名称、需求数量、负责人、准备状态和备注 | 仅活动清单，不提供库存、借还和资产管理 |
| M07 | 反馈与复盘 | 固定评分及文字反馈、执行问题、改进项、活动总结 | 不建设通用问卷；反馈不作为到场证明 |
| M08 | 资料归档 | 活动关联方案、总结、图片及其他附件，按名称查找，归档只读 | 不做文件版本库、独立知识库和语义搜索 |
| M09 | 基础工作台 | 本人待办、活动数、报名数、名额使用率、任务完成情况、活动预算统计 | 数据来自业务记录，不提供综合健康评分 |
| M10 | 必要站内提示 | 任务分派、报名处理结果、关键活动变更、取消及审批处理结果 | 以待办或站内记录呈现，不要求实时推送 |
| M11 | AI 活动总结 | 依据指定活动的授权数据生成总结草稿，支持编辑和确认；与 M12 共用组织模型设置 | 汇总事实与改进建议，不生成考勤结论或预测评分 |
| M12 | AI 方案生成 | 依据活动目标、对象、人数、预算、场地和限制条件生成方案草稿 | 文本建议，不自动转化为活动、任务或支出记录 |

扁平部门或分组作为成员的可选归类信息，不承担权限继承，不增设独立部门负责人角色。没有分组也能完成全部活动流程。

### 3.2 暂不纳入开发的内容

- 签到、定位、扫码核验、二维码凭证、到场统计与出勤评价。
- OCR、票据识别、多模态识图、自动资料分类、自训练模型、智能预测及 AI 自动执行业务操作。
- 在线支付、复杂会计、完整报销、组织月度资金账户和库存借还。
- 即时聊天、短信或邮件通知、原生移动应用、地图调度和离线同步。
- 可配置审批引擎、多级组织树、通用问卷构建器、通用活动模板引擎。
- 资料版本库、全文或语义检索、成员排行榜、综合健康度和跨实体全局搜索。

上述范围不影响手工上传票据或活动图片，也不影响在方案文本中说明活动流程。新增功能须明确解决实际问题，并同步修改交付清单和验收规则，不因页面留有按钮就自动成为需求。

## 四、账号、角色与权限

### 4.1 身份模型

账号是全局登录身份，组织成员是账号与组织之间的关系。一个账号可以在组织 A 担任负责人，在组织 B 作为普通成员，并以外部身份报名组织 C 的公开活动。权限按当前组织及具体活动判断，不能使用一个全局角色覆盖所有组织。

| 身份 | 获得方式 | 主要范围 |
| --- | --- | --- |
| 组织负责人 | 创建组织，或由现任负责人授予 | 管理本组织成员、活动、经费和归档；可有多名负责人 |
| 活动负责人 | 由组织负责人指定，必须是本组织有效成员 | 管理指定活动的任务、报名、物资、执行记录及复盘；可登记支出 |
| 普通成员 | 接受有效组织邀请 | 查看本组织已发布活动、处理本人任务、报名、查看本人记录及提交符合条件的反馈 |
| 外部参与者 | 登录账号后报名公开活动 | 查看公开信息及本人报名结果、取消本人报名、提交符合条件的反馈 |

首期不建设面向业务用户的平台组织审核后台。部署维护身份用于必要的系统维护，不作为跨组织读取业务数据的普通入口。

### 4.2 最小权限矩阵

| 操作 | 组织负责人 | 活动负责人 | 普通成员 | 外部参与者 |
| --- | --- | --- | --- | --- |
| AI 模型配置、测试、启用与密钥管理 | 本组织可操作 | 不可 | 不可 | 不可 |
| 组织设置、成员和负责人管理 | 本组织可操作 | 不可 | 不可 | 不可 |
| 创建活动草稿 | 可创建并指定本组织有效成员负责 | 不可新建；可编辑已指定给本人的草稿 | 不可 | 不可 |
| 提交活动、编辑活动方案 | 本组织可操作 | 本人负责活动 | 不可 | 不可 |
| 活动立项、关键变更确认 | 本组织可操作 | 不可，兼任组织负责人除外 | 不可 | 不可 |
| 分派任务、维护物资及执行记录 | 本组织可操作 | 本人负责活动 | 仅更新本人任务的状态与说明 | 不可 |
| 审核报名、查看完整报名名单 | 本组织可操作 | 本人负责活动 | 仅本人报名记录 | 仅本人报名记录 |
| 登记支出、查看费用明细及票据 | 本组织可操作 | 本人负责活动 | 不可 | 不可 |
| 确认或作废支出 | 本组织可操作 | 不可，兼任组织负责人除外 | 不可 | 不可 |
| 生成、编辑与保存方案草稿 | 本组织可操作 | 本人负责的草稿活动；不获得立项确认权 | 不可 | 不可 |
| 生成、编辑与确认总结 | 本组织复盘活动可操作 | 本人负责的复盘活动 | 不可 | 不可 |
| 编写、保存与确认取消说明 | 本组织已取消活动 | 本人负责的已取消活动 | 不可 | 不可 |
| 归档、取消、重新打开归档 | 本组织可操作 | 可申请或说明，不可最终确认 | 不可 | 不可 |
| 提交反馈 | 满足反馈资格时 | 满足反馈资格时 | 满足反馈资格时 | 满足反馈资格时 |

活动负责人不是独立的全局管理角色，而是账号对某项活动的职责关系。用户同时具有多种身份时，在同一组织和资源范围内合并其明确权限。

权限矩阵与活动状态条件必须同时满足，组织负责人也不能绕过归档只读等约束。取消说明采用手工编写和确认，内容确认不等于取消归档批准；最终取消与归档仍由组织负责人操作，不新增取消活动的 AI 生成入口。

活动负责人不从其负责的另一场活动获得新建活动或自行指派权限。组织负责人先创建活动并指定有效成员，指定者即可编写和提交该草稿；更换活动负责人仅由组织负责人操作并留痕。

### 4.3 账号与组织规则

1. 未登录者可浏览公开活动的已发布基础信息；报名、取消和反馈必须登录。首期使用账号身份去重，不宣称识别现实中同一人的多个账号。
2. 组织创建者成为首位负责人。邀请只授予普通成员身份；提升负责人权限必须单独操作并留痕。邀请需有效期和使用限制，不允许客户端自行指定管理角色。
3. 组织至少保留一名有效负责人。最后一名负责人退出或被移除前必须完成移交；任何成员离开组织前，其未归档活动职责、未完成任务和未就绪物资责任都须转交有效成员或按规则结束，并记录原因。不能只检查活动负责人而遗漏普通成员承担的责任。
4. 成员退出后立即失去内部数据访问权，旧会话不能继续使用旧权限。尚未进入执行的内部活动，其待审或有效报名予以取消并保留原因；已进入执行、复盘或归档的报名保留为历史记录，不因退出改写。公开活动报名仍可按外部身份保留。历史署名、已提交反馈和费用记录不级联删除。
5. 服务端对读取、写入、名单导出、统计和附件访问统一检查身份与资源归属。使用其他组织的活动或成员 ID 创建关联也必须被拒绝。
6. 公开信息只包含发布者明确填写的活动简介、安排和报名条件；任务明细、成员联系方式、票据、反馈原文及内部附件不因活动公开而公开。
7. 账号支持注册、登录、退出、会话过期及控制权恢复。首期通过注册时发放的恢复码验证恢复资格，流程和安全存储见后端架构；不能仅凭公开用户名或组织负责人身份重置他人全局账号。

### 4.4 单级确认与小组织使用

组织负责人承担最终业务确认责任。活动负责人提交后，由组织负责人通过或驳回；组织负责人提交自己的活动或支出时，可以以“负责人自行确认”完成，并记录提交者、确认者及确认类型。存在另一名组织负责人时，可由其审核，记录为他人审核。

首期不强制配置第二位审批人，也不把自行确认表述为独立复核。此规则适用于轻量活动记录，不意味着系统具备职责分离的财务内控能力。开发者独自开发与应用中多个业务用户是不同概念，验收仍需覆盖不同账号和身份。

## 五、活动业务流程与状态

### 5.1 主流程

```text
准备方案 → 草稿 → 待确认 → 筹备中 → 执行中 → 复盘中 → 已归档
                     ↓
                 驳回到草稿

草稿、待确认、筹备中、执行中或复盘中 → 已取消 → 取消归档
报名开放与关闭单独控制，可与任务筹备同时进行。
```

“取消归档”在归档记录中保留取消结果，不被统计为正常完成。流程图描述业务关系，不预先规定数据库字段或代码枚举的实现方式。

### 5.2 状态与操作规则

| 状态 | 允许的主要操作 | 进入下一状态的条件 |
| --- | --- | --- |
| 草稿 | 编写方案、设置负责人、时间、地点、预算、报名范围和名额 | 必填信息及时间规则通过校验后提交 |
| 待确认 | 组织负责人通过或驳回；提交者可撤回 | 通过进入筹备；驳回或撤回返回草稿并保留原因或记录 |
| 筹备中 | 任务分派、准备物资、登记费用、按规则开放报名 | 活动负责人或组织负责人明确启动执行；不根据报名是否关闭自动跳转 |
| 执行中 | 更新任务、记录进展和异常、维护实际费用 | 负责人确认执行结束后进入复盘，未完成任务不会自动完成 |
| 复盘中 | 收集反馈、处理费用、整理改进项、编写及确认总结 | 满足归档条件，由组织负责人归档 |
| 已取消 | 展示取消原因，处理遗留费用和事项，撰写取消说明 | 满足取消归档条件后归档，不允许恢复报名或继续正常执行 |
| 已归档 | 在权限范围内查看记录与附件 | 普通操作只读；组织负责人可说明原因后重新打开 |

单纯保存草稿不对外发布。通过立项确认后，按内部或公开范围展示活动。人员姓名、时间和倒计时由同一份活动数据计算，不使用独立手工文本。处于关键变更待确认期间，任务、物资和费用仅查看已有记录，不继续修改筹备数据；本人合法取消报名及组织退出仍按各自规则处理。

### 5.3 关键变更、取消和归档

- **时间约束：** 活动结束晚于开始；报名开始早于报名截止，报名截止不晚于活动开始。普通参与者可以在活动开始前取消报名，活动启动执行后关闭自助取消。
- **关键变更：** 已确认活动在筹备期调整活动时间、地点、预算额度、报名可见范围或容量时，先撤回到草稿并暂停报名，再修改并重新提交确认。已确认报名和已审核费用保留；新容量不得低于现有有效报名人数，新预算不得低于已审核支出。已有报名后不得切换内部／公开范围，以免产生身份冲突。
- **变更展示：** 再次确认前不将未确认草稿公开给新访问者。已有报名者仍可查看本人报名状态和“活动安排调整中”提示；重新通过后通知已报名者，报名开关默认关闭，由负责人明确重新开启。
- **执行期更正：** 进入执行后，不再撤回立项或任意重写已确认安排。实际地点变化、临时调整和差异通过执行记录说明；不得把事后记录伪装成事前审批。
- **取消：** 组织负责人填写原因后停止报名，未处理报名关闭，有效报名转为活动取消结果；保留名单、已发生费用及操作历史。未完成任务转为取消，遗留事项明确处理人和处理结论，向受影响账号发送站内变更提示。
- **正常归档：** 报名审核已结束，支出无待审项，总结已确认；未完成任务、未就绪物资和未解决问题须完成、取消或在总结中说明处置与责任人。归档不会为了满足条件伪造任务完成。
- **取消归档：** 处理遗留费用及事项，确认取消说明即可，不强制收集活动体验反馈。
- **归档更正：** 只有组织负责人能重新打开并记录理由。正常活动返回复盘，取消活动返回取消处理；不重新开放报名或反馈。更正后重新确认总结或取消说明并归档，保留前次确认内容和更正记录，不建设通用文件版本库。

## 六、各业务模块的具体边界

### 6.1 任务与执行记录

任务归属于单个活动，负责人必须是本组织有效成员。任务至少包含标题、说明、负责人、截止时间、优先级和状态；状态采用待处理、进行中、已完成、已取消。逾期依据截止时间和当前状态计算，不建立另一套手工“风险等级”。

组织负责人或活动负责人可分派、修改、取消和重新打开任务；普通成员只能推进本人任务并提交说明。记录完成时间，重新打开后不再视为当前已完成，保留历史变更。首期没有“待审核”任务状态。

任务创建、分派及物资准备发生在筹备和执行期间；复盘期仅处理既有未结事项，不能新建任务来获取反馈资格。成员只能将本人任务从待处理推进到进行中或已完成，或从进行中推进到已完成；不能将已完成任务退回。取消、重新打开及改派均由管理者执行。取消活动的任务不能重新打开为正常执行。

执行记录由组织负责人或活动负责人填写，用于说明活动推进、问题、临时安排和处理结果。它不记录个人考勤；活动总结不得根据任务完成推断全体报名者已经参加。

### 6.2 报名与名单

报名采用固定字段：账号身份、展示姓名及必要备注；确有联络需要时提供联系方式字段并说明用途。默认不收集身份证号、性别、定位等与本场景无关的信息。

| 规则 | 本版规定 |
| --- | --- |
| 报名开放 | 活动处于筹备中、开关开启、当前处于报名时间窗，且账号满足内部／公开范围要求 |
| 名额 | 采用正整数容量，不提供不限额模式；所有报名人工审核，批准时才占名额 |
| 报名状态 | 待审核、已通过、已驳回、本人取消、组织取消；保留处理原因及时间 |
| 重复报名 | 同一活动同一账号仅有一条报名主记录；取消或驳回后仍在开放期内可以重新申请，更新原记录并保留历史 |
| 并发批准 | 检查剩余名额与占用名额须作为不可分割的业务操作完成；最后一个名额只能授予一个账号 |
| 申请与审核时间 | 申请窗口关闭或报名开关关闭仅停止新申请；筹备中且未到活动开始时间仍可批准已有申请。到开始时间后不再批准，但可驳回待审或按规则组织取消；进入执行前清空待审 |
| 本人取消 | 活动开始前且未进入执行时，登录账号可取消本人待审或已通过报名；已占名额仅释放一次 |
| 组织取消 | 活动进入执行前，管理者可以说明原因取消报名；重复处理不能再次释放名额。进入执行后不再以取消报名修改开始前的接受结果，必要更正在执行记录中说明 |
| 结束审核 | 进入执行前处理所有待审核报名；未获批准的申请明确驳回，不允许事后补录为“已到场” |
| 名单管理 | 管理者可筛选并导出本活动名单；导出沿用权限与字段范围限制并记录操作 |

界面提供“我的报名”作为查看结果和取消的入口，不生成扫码凭证。活动执行后报名状态代表开始前的接受结果，不能反向用来判断是否到场。

### 6.3 活动预算与支出

每个活动维护一项明确的预算额度，使用人民币；零预算活动也可以立项。支出登记用于记录已经发生、需要负责人核对的费用，不同时承载事前资金申请与事后支付结算。

支出包含用途、金额、发生日期、经手说明、分类和凭证附件。分类为简单归类；没有票据时须填写无票说明，不由 AI 识别金额。

支出处理链路为：**草稿→待确认→已确认／已驳回；驳回后可修改重提，已确认后只能作废或另建更正记录。** 更正同一笔已确认费用时，先作废原记录，再建立关联原记录的新登记，重新确认，避免两笔同时计入。负责人自行确认按第四节留痕。重复确认不得重复累计，确认与驳回冲突时只能有一个有效结果。

金额必须大于零并精确保存；预算允许为零，不允许负数。实际费用可能超预算，系统应明确提示并要求组织负责人说明后确认，不能为了让预算好看而拒绝记录已发生的真实费用。预算余额可以为负数，已确认支出不代表系统完成了付款。

首期只显示活动预算、待确认支出、已确认支出及预算余额，不展示未定义来源的组织月预算、账户余额或“本月节省”。

### 6.4 物资准备

物资记录仅服务于活动准备，包含名称、需求数量及单位、负责人、待准备／准备中／已就绪／已取消状态和备注。数量必须有效，不维护跨活动库存，不处理借还、资产折旧或损耗结算。活动负责人根据实际情况更新状态，系统不因任务完成而自动认定物资就绪。

### 6.5 反馈、改进项与总结

活动首次进入复盘后开放反馈，首次归档时永久关闭该活动的反馈新增和普通修改，重新打开归档不恢复反馈入口。可以提交反馈的账号为：活动进入执行时已获批准的报名者，以及执行结束时记录的活动负责人和曾被指派过且截至执行结束任务未取消的账号。任务归属变更以既有历史核对，这只表示系统分工，不证明实际到场；不通过复盘期新增／改派任务补造资格。内部参与身份须仍是有效组织成员；公开活动的报名者可按外部身份提交。活动取消后停止收集体验评分，保留已发生反馈作为历史，不参与正常完成活动的评价汇总，改由负责人记录取消复盘。

每账号每活动一份反馈，仅首次归档前且活动未取消、本人当前仍有资格时可修改；采用固定的 1～5 分总体评分和文字建议，不提供匿名承诺，不建设动态题型。原始反馈仅对组织负责人、活动负责人及当前仍有访问资格的反馈本人可见，不开放给其他报名者。

由于不核验现场参与，反馈代表有资格账号的主动表达，不等同于经验证的现场评价。系统不计算到场率或出勤率，也不把未反馈者视为未参加。

总结至少包含活动目标、执行概况、任务和报名汇总、经费情况、反馈要点、问题及改进项。改进项以文字记录处理人、处理结果或后续安排，不额外建设跨活动整改工作流。用户可以全部手工填写，也可以使用 AI 草稿；无反馈时明确显示“暂无反馈”，仍可完成总结和归档。

总结确认保存当时的相关数据来源版本或摘要；费用、任务、反馈等来源在确认后变化，则标记需要重新核对，不能带着已失效的确认状态直接归档。方案及总结的确认历史保存独立快照，普通编辑不得覆盖前次确认内容。

### 6.6 附件与归档

附件必须关联组织及具体活动或其业务记录。方案、总结、图片与票据等按用途展示，不建立独立知识库；票据仅管理者可见，任务附件按任务访问权限提供。组织负责人及该活动负责人可维护允许状态下的活动资料；普通成员仅可维护本人任务允许的附件，不能上传或查看票据。已确认、被引用或归档的资料遵守保留规则，公开活动不自动公开任何内部附件。

上传、预览、下载和删除都检查业务权限。采用允许类型和大小限制，校验内容，不信任扩展名或原始文件名；存储地址不可绕过权限访问。附件类型、容量上限和保留方式在具体设计中定值并测试。

删除仅适用于尚未确认、无关联依赖的草稿或附件。已经确认的费用、归档资料和审批历史保留，通过作废或重新打开后更正处理。数据库及附件纳入同一恢复方案；操作日志、软删除和备份各司其职，不能相互替代。

### 6.7 站内提示

系统记录任务分派、审批结果、报名处理、关键活动变更和取消等必要提示，用户进入系统后可查看。截止临近和逾期直接在待办中根据时间计算，不要求后台定时群发。

提示只包含必要摘要，列表和详情都重新校验权限；成员撤权后不能通过旧消息读取内部数据。本期站内提示行与业务同事务保存必要接收人和来源，提交后即可读取；登记失败则整体回滚，来源唯一键防重，不需要另设投递队列或定时补建。不能只在内存中排回调而丢失接收者。自助报名取消、活动取消等重复请求不产生重复的有效业务结果。

## 七、AI 亮点设计

### 7.1 AI 活动总结

入口位于活动复盘页面，由组织负责人或活动负责人主动触发。

| 项目 | 规定 |
| --- | --- |
| 输入 | 当前活动的目标与已确认方案、任务汇总、执行说明、报名汇总、已确认费用及授权反馈 |
| 输出 | 目标与执行概况、主要成果、反馈要点、存在问题、改进建议的文字草稿 |
| 事实边界 | 人数、费用、比例等由程序先计算；模型不得创造到场人数、未记录成果或不存在的反馈 |
| 用户操作 | 预览输入范围、生成、编辑、保存草稿、确认作为活动总结 |
| 数据变化 | 生成后来源发生变化时提示重新核对；不得自动覆盖人工编辑或已确认总结 |
| 无数据或故障 | 显示缺失信息或失败原因，保留已有文字，允许继续人工编写 |

总结以单场活动为单位，不另外建设周报调度、全组织分析和自动推送报告。模型提出的改进意见标为建议，不能与已发生事实混写。

### 7.2 AI 方案生成

入口位于活动草稿的方案编辑区，不提供脱离活动的全局聊天助手。

| 项目 | 规定 |
| --- | --- |
| 输入 | 活动主题、目标、面向对象、预计人数、预算范围、时间地点条件和用户补充限制 |
| 输出 | 方案概述、建议流程、分工建议、物资与费用建议、注意事项和备选安排 |
| 缺失信息 | 明确标注假设或待补充项，不伪造已确定场地、合作方和报价 |
| 预算与事实 | 建议金额仅是估算，不代表实际价格或获批预算；不得改写活动预算字段 |
| 用户操作 | 生成、编辑、确认保存为活动方案；需要任务或物资时由用户手工建立 |
| 重新生成 | 先展示新草稿，未经明确替换不覆盖已有编辑内容 |

方案生成只提供构思支持。AI 草稿的“确认保存”不等于活动立项通过；活动仍须按第五节提交并由组织负责人确认。

### 7.3 两项 AI 功能的共同约束

1. 服务密钥保存在服务端；调用前校验当前活动权限，模型无业务写入、审批或跨组织查询能力。
2. 只提供本次生成必需的数据，不发送联系方式、账号凭据及无关组织资料。用户输入和反馈中的指令作为待处理内容，不得改变权限或触发业务操作。
3. 记录生成类型、活动、操作者、模型标识、生成时间、输入范围或来源版本、输出及人工确认状态；普通运行日志不重复保存敏感原文。
4. 有限等待、有限重试，重复点击不得无控制地重复调用；单次输入量及调用额度在模型服务确定后配置。超时或输出无效时说明失败，不冒充生成成功。
5. 生成内容必须以安全文本方式呈现，不执行其中的脚本或指令。人工确认仅保存内容，不授予模型任何额外权限。
6. 总结和方案都必须展示一次真实模型调用及故障后的人工操作；不能用固定模板或演示文本冒充实际调用。固定模板可以作为手工填写辅助，但须明确标识。

两项功能共用组织模型配置、两种兼容协议的文本调用、权限和错误处理能力，不建设智能代理、多模型调度、提示词管理平台或知识检索系统。

### 7.4 组织设置中的模型配置

入口为“组织设置 → AI 模型”。每个组织维护一套当前配置，活动总结和方案共用；只有本组织负责人可查看配置详情、修改、测试、启用或清除密钥。活动负责人可按既有活动权限使用生成，只读取是否可用及模型显示信息；普通成员和外部参与者不能配置或调用。不建设平台全局密钥池、个人配置覆盖、自动切换或负载均衡。

设置包含兼容协议、完整 API 请求地址、模型 ID、API Key、启用状态和受部署上限约束的输出长度／超时。协议支持 OpenAI Chat Completions 和 Anthropic Messages；厂商与协议分开，DeepSeek、GLM、Kimi 等只要具体接口兼容即可配置，不为每个品牌建立一套业务模块。请求地址采用完整端点，页面明确示例，不自动猜测或重复拼接 /v1 等路径。

流程为填写并保存配置 → 手动测试连接 → 启用 → 在活动中生成。未通过当前配置版本的测试不能启用；修改协议、地址、模型、密钥或调用参数后重新测试。测试仅发送固定短文本，不发送组织资料，明确可能消耗少量额度；保存本身不调用模型。测试通过只证明当次基础文本调用可用，不承诺长期可用或所有高级能力。

已保存密钥不回显，仅显示“已配置”；留空表示保留，替换和清除是明确动作。修改目标地址或协议时必须重新输入密钥，不允许将旧密钥静默发送到新地址。清除密钥同时停用；未配置、停用、解密失败或服务不可用时，核心业务及手工方案／总结继续可用。

生成使用启动时的组织配置版本；配置修改／停用后不再发起新调用，已经发出的调用可能仍计费，不能宣称已撤回。返回时重新校验身份、活动及配置版本，旧配置结果不直接替换当前编辑内容。配置操作保留脱敏审计，技术规则由后端架构维护。

## 八、工作台与指标口径

### 8.1 页面职责

组织负责人工作台展示组织层面的待确认事项和活动概览；活动负责人聚焦本人负责活动；普通成员以本人任务、报名和提示为主。外部参与者通过公开活动和“我的报名”使用系统，不进入内部运营工作台。

每个汇总值都必须能说明时间范围及数据来源，并进入有权查看的明细。“我的待办”只列本人尚未处理的任务或确认事项，其他成员的任务单独放在管理视图，已完成项默认不列为待办。

### 8.2 基础指标字典

| 指标 | 统一定义 | 特殊情况 |
| --- | --- | --- |
| 进行中活动数 | 当前组织中处于筹备中或执行中的活动数量 | 不含复盘、取消和归档；复盘待办单独列出 |
| 待处理任务数 | 当前权限范围内，状态为待处理或进行中的任务数量 | 本人视图仅筛选本人；不含已取消任务 |
| 逾期任务数 | 未完成、未取消且截止时间早于当前服务端时间的任务数量 | 不直接标为 AI 预测风险 |
| 活动任务完成率 | 当前已完成任务数／当前未取消任务总数 | 分母为零显示“—”；重新打开后按当前状态计算 |
| 有效报名人数 | 当前已通过且未取消的报名记录数量 | 是报名人数，不代表到场；取消活动显示历史处理记录，不显示正常招募进度 |
| 名额使用率 | 有效报名人数／活动容量 | 容量为正整数；不得称为报名转化率 |
| 反馈份数及平均评分 | 已提交的有效反馈份数；评分总和／评分份数 | 无反馈显示“暂无反馈”和“—”；不据此推断全体成员满意度 |
| 已确认支出 | 状态为已确认且未作废的支出金额合计 | 不计草稿、待确认或驳回；不表示已支付 |
| 待确认支出 | 状态为待确认的金额合计 | 与已确认支出分开，不重复扣减预算 |
| 预算余额 | 活动预算额度－已确认支出 | 可为负数；名称不用“可用资金” |

所有金额保留一致的精度，汇总与明细使用相同过滤规则。所有日期、星期、报名窗口和倒计时使用统一时区及时间基准，界面展示的数据精度和取整方式一致。不提供性别比例、组织健康评分、实际参与率、到场率或无数据来源的增长曲线。

## 九、数据关联与可靠性要求

本节规定业务必须满足的约束，数据库与框架实现见后端架构；概念关系不代替实际建表设计。

配套[概念 ER 图](../图示成果/项目ER图.html)采用矩形实体、椭圆属性和菱形联系，提供总体主干与局部视图。图中“活动文稿”以类型区分方案和总结，AI 生成记录独立保留；其余辅助实体用于表达现有业务要求，不代表新增功能或已确定物理表结构。

| 数据关系 | 必须成立的约束 |
| --- | --- |
| 账号与组织成员 | 同一账号在同一组织仅有一条有效成员关系；不同组织角色互不影响 |
| 活动与关联业务 | 任务、报名、支出、物资、附件、反馈和总结均可追溯到同一活动与组织 |
| 负责人和任务指派 | 内部责任人是有效组织成员；离开组织须先完成未结责任移交 |
| 报名 | 活动与账号唯一，重复请求不重复建立记录，名额更新与状态更新一致 |
| 费用与确认 | 同一记录的确认、驳回或作废遵守当前状态约束，金额只累计一次 |
| 反馈 | 活动与账号唯一，修改保留必要时间信息，归档后关闭普通修改 |
| 总结和方案 | 人工内容与新生成草稿不互相静默覆盖，确认内容有来源及确认记录 |
| 关键操作 | 保留操作者、时间、对象、前后状态和原因；日志仅授权用户可查看 |
| 归档和删除 | 已确认或被引用的记录不直接物理删除，历史关系与恢复数据保持一致 |

并发、唯一性和重复请求保护必须在服务端及持久化层成立，不能依赖前端按钮禁用。具体事务与冲突控制遵守后端架构，在对应模块实现后用反例验证。

不同组织的授权检查覆盖列表、详情、创建、修改、关联、搜索、统计、导出和附件。失效会话或权限撤销应即时阻止后续访问；报错不得泄露其他组织的内容。

## 十一、验收标准

以下是实现应满足的标准，本计划书本身不代表这些检查已经通过。所有必做模块可在同一套系统和同一场活动中贯通，不以分别展示静态页面代替。

| 编号 | 验收场景 | 预期结果 |
| --- | --- | --- |
| A01 | 组织负责人创建活动，经确认进入筹备，完成任务、报名、经费、执行记录、反馈、总结与归档 | 全流程关联同一活动；不依赖签到；重新登录或重启后数据仍在 |
| A02 | 组织只有一位负责人，由其创建并确认活动与支出 | 可完成业务，明确标记负责人自行确认，不伪装成他人审核 |
| A03 | 另一个账号作为活动负责人提交，组织负责人驳回再通过 | 权限及状态正确，提交、修改和处理历史可追溯 |
| A04 | 同一账号加入两个组织，再尝试跨组织详情、关联写入、统计、导出和附件访问 | 身份分别生效；不属于授权范围的数据与写入全部拒绝 |
| A05 | 成员退出、负责人移交后使用旧会话和旧提示访问 | 权限按新状态生效；内部报名及未结责任按规则处理，历史记录保留 |
| A06 | 公开活动报名、结果查询与取消（适配手机浏览器）：登录账号后报名，查询审核结果，再在允许取消的时间内取消 | 电脑与手机浏览器使用同一 Web 系统；不产生组织成员身份，无扫码或定位要求，取消只释放一次名额 |
| A07 | 重复报名、两个账号竞争最后一个名额、取消后重新申请 | 同账号不重复建主记录；最多一个获得最后名额；历史和人数一致；申请截止后、活动开始前仍可审核已有申请 |
| A08 | 已有报名后改期、重新确认，或直接取消活动 | 调整期停止新报名，结果对受影响用户可见，取消后不能继续正常报名 |
| A09 | 多人重复或冲突确认支出，并录入超预算费用 | 无重复累计；冲突明确处理；超支有提示与负责人说明，原始记录不被覆盖 |
| A10 | 无报名、无任务、无反馈、零预算及作废支出 | 统计不除零、不重复计入，仍能按规则记录执行和完成总结 |
| A11 | 只有已批准报名者、活动负责人及任务承担者尝试反馈，其他账号越权提交 | 按第五、六节的状态和资格校验；每账号一份，不宣称验证到场 |
| A12 | 手工总结、真实 AI 总结、来源变化后重新生成 | 两种编写方式可用；人数费用可复核；新草稿不静默覆盖人工内容 |
| A13 | AI 方案生成，输入不完整或预算受限，再确认保存 | 缺失条件标明，建议与事实分开；不自动建立任务、改变预算或批准活动 |
| A14 | 模型超时、额度不足、输出无效或输入含诱导指令 | 不执行越权操作，不虚报成功；原内容保留，用户可手工继续 |
| A15 | 超大或伪装类型文件、跨组织下载、普通成员读取票据 | 被拒绝；授权用户能正常上传与读取允许文件 |
| A16 | 正常归档、取消归档、普通修改及负责人重新打开更正 | 归档只读；原取消结果不丢失；更正留痕并需重新确认；不恢复报名或反馈；总结来源变化需复核 |
| A17 | 从工作台进入明细并复算任务、报名及经费数据 | 公式、范围、精度一致，不出现到场指标、伪造趋势或固定业务数字 |
| A18 | 在独立测试环境重建系统并恢复数据库及附件 | 记录与文件一致可读，配置和操作步骤可复现 |
| A19 | 分派任务、维护物资清单、成员更新本人任务，普通成员尝试修改他人任务或物资 | 管理者与普通成员权限符合矩阵，物资状态不会随任务状态自动变化，接收者可查看分派提示 |
| A20 | 注册、恢复码找回、修改密码、退出和会话过期；携带旧会话或缺失 CSRF 的写请求 | 控制权必须验证，恢复码不能重复使用，旧认证版本失效，错误结构和日志不泄露凭据 |

AI 验收使用固定样本，分别覆盖总结与方案的正常输入、资料不足、相互矛盾、敏感信息、诱导性文字和服务失败；保留输入范围、结果、人工修改及判断记录。评价重点是内容符合输入、主要问题有覆盖、事实和建议分开，不采用仅凭生成字数判断成功的方式。

容量、响应速度、文件限额和模型调用上限在具体设计中依据运行环境确定，记录测试条件及实际结果；本版不预设未经验证的性能数字。并发名额不超限、金额不重复和组织权限隔离不因性能目标调整而降低。
