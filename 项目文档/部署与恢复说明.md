## 二、从源码与配置示例重建

先在 MySQL 客户端执行以下 SQL 模板，替换账号主机和密码。迁移账号权限限定在目标库；已有账号不要重复创建。

```sql
CREATE DATABASE activity_prod CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'activity'@'127.0.0.1' IDENTIFIED BY '<替换为强密码>';
GRANT ALL PRIVILEGES ON activity_prod.* TO 'activity'@'127.0.0.1';
```

从工作区根目录复制配置示例（仅在目标配置尚不存在时执行），填写目标数据库连接与外置 AI 主密钥，不能覆盖已有配置：

```powershell
$backendPath = Join-Path (Get-Location) '基于Vue3的多组织活动管理系统_zcode/backend'
New-Item -ItemType Directory -Force (Join-Path $backendPath 'config') | Out-Null
$configPath = Join-Path $backendPath 'config/application-local.yml'
if (Test-Path -LiteralPath $configPath) { throw '配置已存在，请就地核对，不覆盖。' }
Copy-Item -LiteralPath (Join-Path $backendPath 'src/main/resources/application-local.example.yml') -Destination $configPath
```

配置完成后，在后端目录按 README 启动；Flyway 自动应用未执行迁移。在另一个终端的前端目录执行 `npm ci`、`npm run build`，将 `dist/` 交给反向代理。迁移与启动会写数据库，执行前再次确认目标。

迁移文件共 19 个（`backend/src/main/resources/db/migration/V1__baseline.sql` … `V19__ai_config_generation.sql`），全部为增量且幂等登记在 `flyway_schema_history`；**不要**对已有库手工改表，结构变更一律新增迁移文件。

**本机实测（2026-09-13，空库重建）：** 创建空库 `activity_p9_build` 后启动应用，Flyway 依次应用 V1→V19，`flyway_schema_history` 最新版本 19 且 `success=1`，库内共 19 张表（18 张业务／基础表 + `flyway_schema_history`），`GET /api/health` 返回 `{"status":"UP","database":"UP"}`。

## 三、附件、备份与恢复

**附件目录：** `app.upload.dir`（默认 `./uploads`，相对后端工作目录）。生产必须指向持久磁盘或挂载卷，并把该目录纳入备份范围；数据库只保存登记与元数据，文件本身在磁盘上，两者要配套。

维护窗口先暂停业务写入，等待在途上传和模型调用结束。以下模板从工作区根目录执行，`$backupPath` 必须是本次新建的备份目录；使用客户端文件输出避免 PowerShell 重定向改变 SQL 编码。

```powershell
$mysqlBin = 'C:/Program Files/MySQL/MySQL Server 8.4/bin'
$backupPath = 'D:/backup/activity-prod-本次备份'
$uploadPath = Join-Path (Get-Location) '基于Vue3的多组织活动管理系统_zcode/backend/uploads'
# 若 app.upload.dir 已自定义，先把 uploadPath 改为其实际绝对路径。
New-Item -ItemType Directory -Path $backupPath -ErrorAction Stop | Out-Null
& "$mysqlBin/mysqldump.exe" -h 127.0.0.1 -u root -p --single-transaction --routines --triggers --set-gtid-purged=OFF --default-character-set=utf8mb4 "--result-file=$backupPath/activity_prod.sql" activity_prod
if ($LASTEXITCODE -ne 0) { throw '数据库导出失败，本次备份不可用。' }
Copy-Item -LiteralPath $uploadPath -Destination (Join-Path $backupPath 'uploads') -Recurse -ErrorAction Stop
```

恢复到独立空库及新附件目录，勿覆盖运行环境。先在 MySQL 中创建 `activity_restore`，再使用客户端 `source` 命令导入（PowerShell 不支持 `<` 输入重定向）：

```powershell
& "$mysqlBin/mysql.exe" -h 127.0.0.1 -u root -p --default-character-set=utf8mb4 activity_restore "--execute=source $backupPath/activity_prod.sql"
if ($LASTEXITCODE -ne 0) { throw '数据库恢复失败，停止后续启动。' }
$restoreUploadPath = 'D:/restore/activity-uploads-本次恢复'
if (Test-Path -LiteralPath $restoreUploadPath) { throw '恢复目录已存在，请选择新的空目录。' }
Copy-Item -LiteralPath (Join-Path $backupPath 'uploads') -Destination $restoreUploadPath -Recurse -ErrorAction Stop
```

用独立配置将 `spring.datasource.url` 指向恢复库、`app.upload.dir` 指向恢复附件目录、`server.port` 指向空闲端口后启动。AI 密文恢复还需要对应的主密钥及 keyId，由部署侧安全保管，不能只备份数据库便宣称模型配置可恢复。核对业务记录、全部有效附件引用及真实下载，再恢复写入。

**本机实测（2026-09-13）：**

| 步骤 | 结果 |
| --- | --- |
| 数据库导出 | `activity_test` 导出 25.7MB（`--single-transaction --routines --triggers`） |
| 附件目录备份 | 运行时持久目录 `backend/uploads` 共 34 个文件全部复制 |
| 恢复 | 导入独立库 `activity_p9_restore`：19 张表；活动 3604、报名 1086、支出 219、附件登记 538、AI 生成记录 489、反馈 29；`flyway_schema_history` 最新版本 19 |
| 关联核对 | 备份的 34 个附件文件与恢复库中的登记行**一一对应** |
| 可读取性 | 用恢复库启动实例（端口 8099）：`/api/health` UP、`/api/public/activities` 返回 119 条公开活动，说明恢复后记录可正常读取 |

**必须记录的一条运行时说明：** 该测试库同时被自动化测试使用，而测试按 R08 把上传目录指向临时目录并在进程退出后清理，因此 538 条附件登记中有 504 条指向已清理的临时文件，只有 34 条属于运行时持久目录。**这仅证明恢复实例及这 34 个文件可读，不能证明完整附件集恢复通过。生产必须核对所有仍应保留的附件登记及实际文件，缺失引用不能因目录已复制而忽略**；核对方法：

```sql
-- 导出全部 stored_name，与上传目录文件清单比对，缺文件的行即为不一致
SELECT stored_name FROM attachment;
```

## 四、生产构建与反向代理

前端是标准 SPA（Vue Router history 模式），反向代理必须把未知路径回退到 `index.html`，并把 `/api` 转发到后端；后端只需 8080 一个端口。**本机实测（`node .\生成脚本\audit_p9_build.mjs`）**：用最小静态服务器（未知路径回退 `index.html`、`/api` 反向代理到 8080）提供 `dist/`，`/` 与 `/org/1/activities/1` 均返回应用入口且引用哈希资源（`/assets/index-*.js`，`text/javascript`），浏览器打开嵌套路由被守卫重定向到登录页并正常渲染表单，深链接 `/public/activities/1` 渲染公开列表，`/api/health` 经代理返回 UP，页面错误 0。

会话与安全相关：生产必须用 HTTPS，并把 `server.servlet.session.cookie.secure` 置为 `true`（开发环境为 false）；CSRF 由 Spring Security 的会话令牌提供，前端写请求自动携带。

## 五、AI 模型接入（可选功能）

AI 是可选亮点，未配置、停用或不可用时方案与总结仍可手工完成。生产部署需要：

| 参数 | 来源 | 建议 |
| --- | --- | --- |
| `app.ai.enabled` | 环境变量 `ACTIVITY_AI_ENABLED` | 需要 AI 时 true；否则 false（入口返回 503 `AI_DISABLED`） |
| `app.ai.master-key` | 环境变量 `ACTIVITY_AI_MASTER_KEY`，Base64 的 32 字节 AES 密钥 | **必须由部署侧保管**，不进库不进仓库；轮换时同时改 `master-key-id` 并让组织重新录入密钥 |
| `app.ai.allowed-hosts` | 环境变量 `ACTIVITY_AI_ALLOWED_HOSTS` | 只列实际使用的模型域名（支持 `*.example.com`）；新增可信网关时扩充 |
| `app.ai.allow-private-hosts` | 环境变量 | **生产必须 false**；true 只允许本机桩服务验证使用 |
| `app.ai.max-concurrent-calls` / `max-calls-per-day-per-org` | 环境变量 | 按模型服务额度设置；当日额度按持久生成记录统计（含连接测试） |
| 组织级配置 | 界面「组织设置 → AI 模型」 | 协议、完整端点、模型 ID、密钥、输出上限字段与上限、时限；保存→测试→启用 |

出口限制：除应用内的域名白名单与公网地址校验外，部署侧应限制出网目标（只允许已登记模型域名），应用不声称一次 DNS 检查即可替代受限出口。测试连接只发送固定短文本，仍会消耗少量额度。

## 六、已知限制

1. **真实厂商模型未接入**：本机验收用桩模型服务核对协议与编排，真实模型的文本质量、厂商限流与计费额度未实测；接入后需按[历史验收记录](历史记录/验收复核记录.md)第二节第 1 条补齐证据，当前结论以[审核报告](开发进度审核报告.md)为准。
2. **性能结论限于单机开发环境**：`audit_p9_flow.mjs` 记录的常规读写 5～35ms、模型连接测试 52ms 均为单机单请求观测值，未做并发压测；并发正确性由名额、金额与锁的用例保证，不因性能目标调整而降低。
3. **注册与登录限流为首期进程内实现**：单实例部署下有效；多实例部署需要外部限流（未纳入本期）。
4. **站内提示只有站内渠道**：投递即意图行本身，不部署外部渠道与投递队列重试（已记录为最小例外）。
