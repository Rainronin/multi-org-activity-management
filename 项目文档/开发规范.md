# 基于 Vue 的多组织活动管理系统设计与实现

## 开发规范

状态：当前工程与接口约定；正式工程已存在，本文规定实现要求，当前达成情况见[开发进度审核报告](开发进度审核报告.md)。业务事实以[项目计划书](项目计划书.md)为准；前后端内部结构分别见[前端架构](前端架构与技术栈设计.md)和[后端架构](后端架构与技术栈设计.md)。

## 一、最少且充分的工程规则

- 一个工作区、一套前端、一个后端应用、一个关系数据库。业务模块通过代码边界隔离，不按模块建立独立服务或构建工程。
- 新实现先搜索同类代码，再选标准库、平台或现有依赖；新增依赖须说明现有能力为何不足，并同步依赖清单和锁文件。不默认引入通用 CRUD、事件总线、请求缓存、状态机引擎或多模型框架。
- 按功能逐步建立 `frontend/`、`backend/`；没有实际文件就不创建空目录。`项目文档/` 放当前规范，`图示成果/` 是辅助设计图，`生成脚本/` 放可复用生成和检查脚本，`历史参考/` 默认不参与开发上下文。
- 文档就地维护，不以 `v2`、`final`、`新版` 副本并列保存当前规则。业务变更改计划书及受影响清单，接口变更改本规范或对应模块接口说明，目录变更改对应架构；README 只索引，不复制正文。
- UTF-8 文本；中文注释解释业务原因，代码标识符使用英文。前端 Vue 组件和 Java 类用 PascalCase，函数与变量用 camelCase，SQL 表和列用 snake_case，错误码及固定状态值用 UPPER_SNAKE_CASE。
- 前端开启 TypeScript strict，采用 ESLint 与单一格式化配置；后端使用编译器、测试及 IDE 格式设置，不为形式统一叠加多套检查器。不得用 `any`、忽略检查或关闭校验掩盖类型与业务错误。
- 工程初始化时记录 Node、JDK、包管理工具和依赖确切版本，提交 npm 锁文件及 Maven Wrapper，配置可重建。凭据、上传文件、日志、构建产物和本机路径不提交。
- 根目录使用一套 Git 仓库；原型保持在 `UI演示/`，正式代码进入 `frontend/`、`backend/`，不复制原型的 package.json、假数据或权限逻辑。提交按一个可验证的小目标组织，不自动提交未完成工作或推送远端。
- UI 基线已确认，视觉与交互以[前端 UI 设计与规范](前端UI设计与规范.md)为唯一来源。所有项目视觉数值集中为 token，优先复用 Element Plus，禁止页面硬编码或同义包装；演示不能替代业务验证。

## 二、接口合同唯一约定

### 2.1 路径、方法与范围

| 类别 | 路径示例 | 约束 |
| --- | --- | --- |
| 身份 | `/api/auth/login`、`/api/auth/logout`、`/api/auth/csrf` | 登录和退出为 POST；获取 CSRF 为 GET |
| 组织资源 | `/api/organizations/{orgId}/activities/{activityId}` | orgId 表达访问范围，不授予权限 |
| 活动子资源 | `.../activities/{activityId}/tasks/{taskId}` | 同时校验组织、活动与子资源一致 |
| 业务动作 | `.../activities/{activityId}/approve`、`.../expenses/{expenseId}/confirm` | POST，校验预期版本、状态、权限及必要原因 |
| 公开活动 | `/api/public/activities/{activityId}` | 只返回已发布的公开字段 |
| 本人记录 | `/api/me/registrations` | 账号从会话获取，不接收客户端指定的查询账号 |

GET 只读，POST 创建或执行动作，PATCH 更新明确允许的字段，DELETE 仅用于允许删除的草稿或附件。PATCH 区分未传字段与显式 null；服务端拒绝未知或不可编辑字段，不直接将请求对象覆盖数据库记录。状态不通过普通编辑接口任意赋值。

每个业务端点只由一个 Controller 声明；登录、退出由 Spring Security 过滤器处理，不再重复声明 Controller。具体字段在实现该模块前记录到模块接口说明，使用本文约定；不提前写几百个没有业务实现的空端点。对契约做不兼容修改时同步调用者和检查，不保留未经要求的旧版 API。

本地联调统一通过 Vite 将 `/api` 代理到后端，浏览器只请求相对路径，并携带同源会话。正式前端开发默认使用 `127.0.0.1:5174`，后端默认 `127.0.0.1:8080`，原型保留 5173；端口占用时明确报错或显式改配置，不静默漂移。不要混用 localhost 与 127.0.0.1，不为联调开放携带凭据的任意来源 CORS。代理机制见 [Vite server.proxy](https://vite.dev/config/server-options.html#server-proxy)。

### 2.2 成功响应与字段

- 详情返回资源 JSON，不再套 `Result<T>` 或同时使用 `success/code/data` 多层包装；创建成功用 201 返回新资源，更新／动作成功用 200 返回最新资源，无响应体的删除或退出用 204。
- 分页端点固定 `{ "items": [], "page": 1, "pageSize": 20, "total": 0 }`。page从1开始，pageSize默认20、上限100；排序字段白名单，追加ID作为稳定排序项，超界参数返回校验错误。返回`{items}`的列表及本人报名的兼容全量列表按接口说明处理，不能仅凭pageSize字段推断端点支持分页。不预建游标分页框架。
- 标识统一作为字符串传输；版本、容量及通常的计数使用数字，费用 `voucherCount` 保留当前字符串合同，具体例外以接口说明及DTO为准。金额为两位小数的十进制字符串，人民币支出必须大于零、预算非负，超出精度拒绝而非静默舍入；服务端 BigDecimal、数据库 DECIMAL 的容量上限在建表时一致定义。
- 时间点使用带偏移的 ISO 8601，接口优先返回 UTC 的 `Z`；界面按 `Asia/Shanghai` 显示。费用发生日期等纯日期使用 `YYYY-MM-DD`，不得作为 UTC 时间点转换。报名和截止判断以服务端时间为准。
- 响应对象按公开、本人及管理场景明确字段，不直接序列化数据库实体。除校验错误外不返回原始 SQL、内部路径、堆栈或第三方错误正文。

### 2.3 错误结构与职责

采用 Spring 原生 `ProblemDetail`，媒体类型为 `application/problem+json`，增加业务字段；不另造一套异常序列化框架。[Spring 错误响应文档](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html)提供对应能力。

```json
{
  "type": "about:blank",
  "title": "当前状态不允许此操作",
  "status": 409,
  "detail": "报名记录已被处理，请刷新后查看。",
  "code": "REGISTRATION_STATE_CONFLICT",
  "requestId": "由服务端生成的请求标识",
  "fieldErrors": []
}
```

字段错误格式为 `{ "field": "amount", "message": "金额必须大于零" }`，字段路径与输入对象一致；不返回敏感字段的原值。

| HTTP 状态 | 使用场景 | 前端行为 |
| --- | --- | --- |
| 400 | JSON 格式、参数、字段或约束无效 | 显示字段错误或说明，保留输入 |
| 401 | 未登录、会话失效 | 清空已加载的受保护内容，一次登录引导，不让多个请求重复弹窗 |
| 403 | 已知且可见资源上的操作无权执行，或 CSRF 验证失败 | 按错误码区分权限与 CSRF，禁止自动重放写请求 |
| 404 | 不存在或不允许获知存在的组织／资源 | 展示不可访问，不泄露所属组织 |
| 409 | 版本冲突、非法状态、名额不足、请求仍处理中 | 保留编辑，刷新状态后由用户决定 |
| 413 / 415 | 文件或请求过大／不支持的类型 | 提示限制，不将原始文件内容写入日志 |
| 429 | 登录、恢复或模型调用限流 | 显示稍后重试，可提供 Retry-After |
| 502 / 504 | 外部模型失败／超时 | 生成失败，保留人工文稿 |
| 500 / 503 | 内部异常／暂时不可用 | 显示安全提示及 requestId，不冒充成功 |

Controller 使用统一异常映射；Spring Security 过滤器中的 401、403 也输出同一结构，不能返回登录 HTML。代理错误、网络断开或非 JSON 响应由前端转换为本地传输错误，不能假装拿到了业务错误码。

业务层抛出明确的业务异常，未预期异常在边界记录一次并返回 500；不在每层 catch 后返回 null，不用一个 `RuntimeException` 加任意字符串代替业务错误码。数据库约束冲突只有能够识别具体业务语义时才映射为 409。

请求层负责解析和抛错，不弹消息、不直接操作路由；页面处理字段错误与业务反馈，应用会话层处理失效登录。每次失败只由一个展示位置提示，主动取消的读取请求不提示“系统异常”。

### 2.4 登录、CSRF 与缓存

前后端生产环境同源，Cookie 保存会话标识，设置 HttpOnly、Secure、SameSite=Lax，首期空闲会话有效期为 30 分钟；开发环境的 Secure 配置仅按本地协议调整。使用 Spring Security 的登录会话更新与退出失效机制，不自己签发 JWT。

登录采用唯一且简单的接入方式：`POST /api/auth/login`，请求为 `application/x-www-form-urlencoded`，字段 `username`、`password`，由 account/api.ts 使用 URLSearchParams 经统一 HTTP client 发送；其他普通业务仍为 JSON。复用 Spring Security 表单认证过滤器，配置成功返回 204、失败返回本文 ProblemDetail，不重定向 HTML、不另写一套 JSON 密码认证 Controller。此处登录 204 是明确的成功响应例外。登录后通过 `GET /api/auth/me` 读取当前账号，组织目录另取，不让登录返回全局角色。框架接入依据见 [Spring Security Form Login](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/form.html)。

前端启动或进入需要写入的公开表单前，通过 `/api/auth/csrf` 获取 `{ "token": "...", "headerName": "X-CSRF-TOKEN" }`，保存在内存，所有非安全方法带此请求头。登录、退出及恢复改变会话后重新获取 token；CSRF 失败只刷新凭据并提示，不能自动重发提交。遵循 [Spring Security SPA 对接](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

CSRF 首期使用 HttpSessionCsrfTokenRepository；获取端点允许匿名访问并返回所配置处理器实际接受的 token，写请求由同一处理器验证，不自行混用原始值与掩码值，也不额外建设可读 CSRF Cookie 方案。注册、登录、恢复及退出都不能因匿名入口而豁免 CSRF。校验失败使用 `CSRF_INVALID`；错误账号或密码使用 `AUTH_INVALID_CREDENTIALS`，未登录／过期使用 `AUTH_REQUIRED`，均沿用统一错误结构。

前端将会话状态区分为尚未校验、已登录、未登录，网络失败不能直接当作未登录；请求绑定当前会话代次，登录／退出后旧请求的 401 不得清除新会话。登录失败的 401 就地显示，不触发全局重新跳转。登录回跳仅允许已注册的站内相对路由，拒绝外部 URL 和协议相对地址；登录成功后仍验证目标资源权限。恢复码发放／重签页面禁用持久化和日志记录。

受保护 JSON、CSRF、恢复及私有附件响应设置 `Cache-Control: no-store`。禁止 Service Worker 或前端持久缓存保存组织资料、凭据、AI 草稿；已被用户读取或下载的内容无法靠撤权远程收回，撤权保障的是后续请求被拒绝，页面在下次校验时清理已有内容。切回标签页时重新验证会话和当前组织，服务端不依赖前端轮询来撤权。

### 2.5 重复提交、版本和请求标识

requestId 用于追踪单次 HTTP 请求，由服务端生成并在 `X-Request-Id` 及错误体返回；不作为防重键，也不直接信任客户端日志标识。

新建活动、支出、文件上传及 AI 生成等可能重复产生记录或费用的 POST 使用 `Idempotency-Key`。前端在一次用户意图开始时生成并保留 UUID，未知结果的重试沿用原键和内容。服务端以账号、动作、资源范围及键唯一约束，保存规范化内容摘要、状态及结果资源引用；同键异内容返回 409，同键处理中返回 409 `REQUEST_IN_PROGRESS`。上传摘要包含文件内容与归属，不能只比较文件名。

重放仍需验证当前身份、组织和读取结果的权限；权限已撤销不能从旧结果返回敏感响应。最终结果在同一业务事务完成，长期处理中有超时核对入口；文件或模型外部结果不明时，不因重试而自动再执行。首期保留操作防重记录，不提前开发通用清理调度或无限结果缓存。

每个需要防重的动作在接入时，必须同时给出**结果恢复路径**并在接口说明记录，不能只写“稍后查询”：普通数据库创建可以同原端点、原键、原内容重放并返回已提交资源；文件与 AI 则提供所属模块的只读操作状态查询，查询使用原防重键而非 requestId，且重新验证原操作者及资源权限。状态最少区分 `PROCESSING`、`SUCCEEDED`、`FAILED`、`UNKNOWN`，成功结果携带可访问的资源标识；未找到记录不意味着可以换键重做。只有能够证明未产生外部副作用的失败才允许用户发起新尝试；UNKNOWN 只核对，不重新调用模型。查询仅用于这些既有操作，不新增全局任务中心或通用作业平台。

编辑及审批请求携带整数 `version`，服务端以当前状态和版本条件更新。重复报名／取消等有明确业务唯一键的动作优先复用既有记录和状态规则，不为每个 GET 或普通状态查询加防重记录。

### 2.6 模型配置与上游错误

组织模型配置、测试及生成接口同样遵守本文的 CSRF、授权、字段校验、版本与错误合同，具体协议和密钥机制以后端架构 6.4 为准。上游认证失败属于 AI 调用错误，不返回表示本站会话失效的 401；测试只允许服务器向受限模型端点发送固定文本，不开放任意转发请求。

## 三、日志、审计与通知的区别

| 类型 | 内容与位置 | 规则 |
| --- | --- | --- |
| 运行日志 | 时间、级别、requestId、路由模板、耗时、HTTP 状态、错误码；服务端日志文件或标准输出 | INFO 记录必要运行事件；WARN 记录可处理异常与安全拒绝；ERROR 记录未预期异常和堆栈，一次异常只在边界记一次；DEBUG 默认关闭 |
| 业务审计 | 数据库中操作者、组织、活动或业务对象、动作、原因、前后状态／版本、自行确认标记、时间 | 关键业务变更同事务写入，失败则变更回滚；按资源权限查询，不能编辑历史 |
| 通知 | 接收账号、来源业务操作、类型及最少摘要 | 本期仅站内渠道，notification行即提示意图，与业务同事务登记，登记失败整体回滚；无后置外部投递，不可替代审计或计算业务真相 |

不记录完整请求或响应体、密码、恢复码、Cookie、CSRF token、模型密钥、附件内容和模型输入输出原文；URL 使用路由模板，日志中的外部文本去除换行等控制字符。确需保留的方案／总结确认快照及 AI 输出保存在受权限控制的业务记录，不复制到审计 JSON 或普通日志。

配置日志轮转、保存时长和磁盘上限，部署说明给出实际值；不在尚无运行环境时编造性能与容量结论。健康检查仅给必要状态，不开放数据库详情、配置值、堆转储或日志下载给普通用户。

## 四、实现、检查与文档维护

- 前端组件不直接访问数据库或模型，后端 Controller 不直接调用 Mapper。代码边界与跨模块例外以对应架构中的唯一所有者表为准。
- SQL 用 MyBatis 参数绑定，动态排序白名单，禁止把输入拼接进 SQL。数据库迁移应用后不改历史文件；演示重置只能针对明确的独立演示／测试库。
- 先在现有测试中增加能复现问题的最小检查。权限、状态、金额、幂等和并发检查使用真实业务入口；数据库锁和约束使用隔离的真实 MySQL 环境，不能用 mock 或 H2 推断结果。
- 前端工程建立后提供 `npm run typecheck`、`npm run lint`、`npm run test -- --run`、`npm run check:ui`、`npm run build`；后端建立后提供 Maven Wrapper 的 `verify` 入口。当前正式工程已提供这些入口；通过结果及覆盖限制以实际执行和开发进度审核报告为准。
- 每次功能完成更新清单与相关测试证据。所有功能未完成前不勾选对应项；页面外观与交互按 UI 规范落实，不复制原型中的硬编码样式。
- 增加依赖、通用组件或模块时，说明复用点及所属目录；没有真实调用者不建空抽象。需要复杂拆分时先记录解决的具体问题，而非仅写“方便扩展”。

初版工程和清单已完成，数据与接口说明按当前迁移及Controller维护；后续先对照实现核对受影响字段与端点，不将历史待办当作现存缺口。每次任务按用户授权选具体缺陷或需求及可验证流程，不重复生成已有模块，不因设计待细化而搭建通用框架。
