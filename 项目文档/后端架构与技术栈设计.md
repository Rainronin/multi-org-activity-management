# 基于 Vue 的多组织活动管理系统设计与实现

## 后端架构与技术栈设计

状态：当前开发基线，尚未创建工程、数据库或部署。业务规则由[项目计划书](项目计划书.md)定义；接口、错误、日志及构建检查统一遵守[开发规范](开发规范.md)，本文件只定义后端实现职责和可靠性方案。

## 一、语言、框架与最小部署

| 层次 | 当前选型 | 工程规则 |
| --- | --- | --- |
| 语言 | Java 21 | 不用预览特性；金额 BigDecimal；传输对象可用 record |
| 应用 | Spring Boot、Spring MVC | 一个应用，普通 HTTP JSON；不用 WebFlux 或微服务框架 |
| 身份 | Spring Security、Servlet HttpSession | 单实例会话；权限按当前数据库状态判断 |
| 校验 | Jakarta Bean Validation | 格式与范围用现有校验，关联和状态由业务服务处理 |
| 数据访问 | MyBatis | 显式 SQL 与参数绑定；不叠加 MyBatis-Plus、JPA 或通用 CRUD 基类 |
| 数据库 | MySQL 8.4、InnoDB | 单库共享表，组织范围约束；不用分库分表 |
| 迁移 | Flyway | 一条版本化 SQL 迁移路径，不与自动建表并行 |
| 构建 | Maven、Maven Wrapper | 单 Maven 工程；依赖尽量由 Spring Boot 管理，锁定实际版本 |
| 文件 | 服务端受控持久目录 | 文件不进数据库大字段或公开静态目录 |
| AI | Java 标准 HTTP 客户端 | 按组织配置调用 OpenAI／Anthropic 兼容文本接口；不建 Agent、独立 Python 服务或动态插件工厂 |
| 检查 | Spring Boot 测试支持、JUnit、MockMvc、真实 MySQL 测试库 | 测试服务入口、事务与约束，不把 mock 成功当成数据库正确 |

Spring Boot 与 MyBatis Starter 选择同一兼容代际的稳定版本；初始化时记录确切版本并验证编译、登录和事务，不能混用不同版本教程。版本依据为 [Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)和 [MyBatis 兼容关系](https://github.com/mybatis/spring-boot-starter)。

部署一个后端实例与数据库，前后端生产同源；现有 Web 服务转发 `/api` 或由后端提供前端产物均可，部署环境确定时选一种，不同时维护两套方案。会话首期保存在内存，重启需重新登录，业务数据持久保存。没有多实例需求前不引入 Redis、共享会话、消息队列、API 网关或分布式锁。

## 二、目录和依赖方向

下列是目标结构，包名 `com.example.activity` 为示意，初始化时一次确定项目实际根包；无实际文件不预建空目录。

```text
backend/
  pom.xml
  mvnw / mvnw.cmd / .mvn/
  src/main/java/com/example/activity/
    Application.java
    config/                     框架及环境配置，无业务审批规则
    common/                     错误码、分页、时钟等无业务归属能力
    security/                   身份、当前主体、资源授权读取
    application/                真正跨模块的流程及其 Controller
    modules/
      organization/             成员、邀请与组织数据
      account/                  凭据、账号与恢复
      activity/                 活动基础、方案、执行和归档记录
        ActivityController.java
        ActivityService.java
        ActivityMapper.java
        dto/                    请求／响应 DTO，按实际需要拆分
      task/
      registration/
      expense/
      material/
      review/
      attachment/
      notification/
      dashboard/
      ai/
  src/main/resources/
    application.yml             非敏感默认配置
    mapper/<module>/            对应 Mapper XML
    db/migration/               已应用迁移不回写
  src/test/                     测试源码与专用数据
```

普通模块直接放相关类，文件过多再分子包；不强制每个模块都生成 Controller／Service／ServiceImpl／Repository／Manager 等整套空壳。Service 只有一个实现时使用具体类；MyBatis Mapper 接口是框架要求，不能为了“去接口”破坏其机制。SQL 统一在对应 Mapper XML 管理，避免同一查询散落注解和 XML。

### 2.1 依赖规则

- 普通请求：模块 Controller → 本模块 Service → 本模块 Mapper。
- 跨模块请求：application 中的专用 Controller → 流程 Service → 各模块 Service。模块不能反向调用 application；不在普通 Controller 再声明相同动作端点。
- 模块 Service 不互相形成业务调用环；需要跨模块修改时由 application 组合，不用内部 HTTP、事件总线或 `@Lazy` 掩盖循环依赖。
- 模块间确有只读需求时调用所有者提供的具名查询方法，例如费用读取活动预算；方向必须单向，不能为读取方便直接操作对方 Mapper。出现双向依赖时提升到 application 编排，而非放宽目录规则。
- Service 可使用 security 提供的当前身份和授权读取；security 通过只读 AccessMapper 获取最少成员与资源关联，不调用业务 Service。common 不依赖 security、application 或 modules。
- Service 和流程编排可以进入事务；Controller 不管理事务、不直接使用 Mapper。定时／维护入口如后续出现，仍调用相同服务，不能另写一份规则。
- dashboard 查询和 security 授权允许用各自只读 Mapper 跨表读取必要字段，这是明确的读取例外；不得跨模块写表或通过“统计”接口泄露未授权字段。
- DTO 与持久化记录分开，DTO 不携带可信操作者或全局组织角色。简单字段映射手写；有实测维护负担再评估映射库，不先引入反射 Bean 拷贝工具。

## 三、模块所有权与跨模块流程

| 模块 | 拥有的数据和规则 | 对外提供的最小能力 |
| --- | --- | --- |
| account | 账号、密码、恢复凭据、认证版本 | 认证、恢复、账号状态验证；不分配组织角色 |
| organization | 组织、有效成员关系、邀请、组织负责人 | 成员查询及变更；业务职责移交由 application 统一组织 |
| activity | 活动主数据、方案、状态、执行记录、确认及归档快照 | 基础编辑及局部状态操作；不能直接修改任务／报名表 |
| task / material | 任务及历史／物资准备清单 | 本模块查询、维护、责任移交及取消处理 |
| registration | 报名主记录、申请历史、执行时接受结果 | 申请、审核、取消、名单及资格来源，不拥有组织成员关系 |
| expense | 活动支出、凭证关联、确认与作废 | 明细、有效金额查询及费用状态转换；预算字段归 activity |
| review | 反馈、资格依据、总结、取消说明、改进说明、确认快照 | 反馈资格及唯一性、总结／取消说明保存与确认；不能批准或归档活动 |
| attachment | 文件元数据、内容校验、存储与读取 | 根据业务归属提供受控文件操作；不判断费用是否已确认 |
| notification | 提示意图、投递状态及接收人提示 | 来源操作防重、列表与补建；不能改主业务结果 |
| dashboard | 无独立业务真相 | 按授权范围查询计划书指标，复用统一状态口径 |
| ai | 组织模型配置、加密密钥、连接测试、生成请求、输入来源、输出、调用结果 | 仅调用模型并保存生成记录，不保存已确认方案／总结 |

同一概念文稿即使物理上共用表，也由 activity 拥有方案、review 拥有总结的业务操作；禁止两个模块绕过类型和资源范围任意写整张文稿表。完整表结构在数据库详细设计时落实。

仅以下流程进入 application，不将所有 CRUD 都再套一层：

| 流程入口 | 唯一编排责任 |
| --- | --- |
| ActivityWorkflowService | 立项关键变更、开始／结束执行、取消、归档及重新打开；调用各模块检查并处理关联数据，整体事务提交 |
| MembershipWorkflowService | 离组、移除、负责人授予／撤销与职责移交；检查最后负责人、活动、任务、物资及相关报名，再完成成员变更 |
| AiGenerationService | 获取授权的方案／总结输入、创建生成记录、事务外模型调用、复核权限后保存生成结果 |

上述流程的 Controller 放 application，对应动作 URL 仍属于组织／活动资源，不暴露 `/workflow` 通用引擎 API。成员列表、活动详情等普通读取不经过流程编排层。

## 四、身份、账号恢复与授权

登录、Cookie、CSRF、错误格式及缓存行为以开发规范为唯一来源。复用 Spring Security 的认证、密码编码、会话固定攻击防护和退出能力，不手写密码散列或 session ID；参见[密码存储](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)和[会话管理](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)。

### 4.1 无外部通知服务的账号恢复

首期使用账号加密码，注册成功时生成一次性恢复码并要求用户自行妥善保存；恢复码是账号控制凭据，不是报名凭证。使用安全随机源生成至少 128 位随机值，仅向用户显示一次，数据库保存校验摘要、使用状态和失效条件，日志不保存明文。

恢复需账号与有效恢复码，失败统一提示、限流；成功在同一事务中修改密码、使旧码失效、生成新码并递增账号认证版本。会话携带版本，后续请求比较当前账号状态和版本，使旧会话失效；修改密码同样验证控制权。无恢复码且无法证明控制权时不能仅凭用户名人工重置；不新增管理员任意重置网页。

恢复码在使用、重新签发或账号失效前有效，不依赖短期外部消息；展示确认流程在身份模块接口说明中落实。这不需要购买短信或邮件业务通知服务。恢复成功响应丢失不能重复使用已消费的码；用户可用自己刚设置的新密码登录后重新签发恢复码，重新签发须验证当前密码并使旧码失效。

### 4.2 授权边界

每次请求依据当前账号、组织成员、活动职责及资源状态授权，不用登录时的角色快照长期放行。组织负责人可创建活动并指定该组织有效成员为活动负责人；活动负责人仅处理已指定活动，不从另一活动职责获得新建活动权限。

会话不保存全局“当前组织”；orgId 从请求范围取得并经后端核对。SQL 的读写都带资源范围，关联责任人与附件同样验证。必要的复合外键／唯一约束提供数据层防错，不能仅靠统一过滤拦截器假设任意 SQL 都已隔离。

公开活动、本人记录、组织管理分别返回允许字段。外部参与者不获得组织内部读取权限；反馈原文、票据和任务附件按具体权限读取。受限资源返回 404 或明确的操作 403，具体分工遵守开发规范。

## 五、事务的统一规则

### 5.1 简单、可证明的首期锁协议

采用短事务与数据库锁，业务事务隔离级别统一为 READ COMMITTED；不是仅修改隔离级别就保证正确，还必须遵守以下锁顺序：

1. 普通组织业务写入先对组织行加共享锁，校验当前有效成员或外部参与资格；组织成员、负责人变更取该组织行排他锁。
2. 涉及已有活动的写入再锁活动行，多个活动按 ID 升序；之后按各业务表固定顺序访问子记录。
3. 成员退出流程先取组织排他锁，再锁受影响活动并完成职责、报名和成员变化。所有授予、撤销、离组、任务指派路径遵守相同协议。
4. 锁内校验版本、当前状态及权限并修改数据；事务提交前写关键审计和必要通知意图。文件传输、模型调用、响应输出都在锁外。

这样同一活动的写操作会串行，不同活动可并行；成员变更短暂阻塞该组织写入，是明确的首期简化。若实测锁等待影响实际操作，再细化锁范围，不预先引入分布式锁。共享锁不升级为排他锁：成员变更入口一开始就选择排他锁。锁定读取依据 [InnoDB 说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

Service 的事务必须实际经过 Spring 代理；避免同类自调用绕过 `@Transactional`。明确哪些异常回滚，不能 catch 后返回成功导致部分提交，参见 [Spring 事务机制](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。数据库死锁只有在完整事务已回滚、操作可重试且无外部副作用时才有界重试；未知提交结果走防重查询。

### 5.2 报名与容量

首期不保存另一份容易漂移的占额计数。所有影响报名状态和容量的写入遵循活动锁协议，锁内查询当前已通过未取消的报名数，确认小于容量后再批准；READ COMMITTED 下查询应看到前一个已提交事务，且同活动竞争写入被锁串行化。

报名申请要求开关与申请时间窗有效；审核已有申请不要求申请窗口仍开放。批准只在筹备中且早于活动开始时允许，时间到后可以驳回或组织取消以结束待审；开始执行前所有待审必须明确处理。容量变更、组织退出、个人取消、活动取消都使用同一状态更新与锁规则。

数据库保证活动与账号主记录唯一，重新申请更新主记录并保留历史。取消不通过减计数释放名额，而由有效报名集合变化体现，重复取消不产生第二次业务结果。按活动、状态建立实际查询索引，并用两事务争抢最后名额证明正确。

### 5.3 费用、预算及归档

按活动锁内当前有效已确认费用求和，确认时同时检查预算、超支说明、预期版本及状态。支出确认／作废及关键审计原子提交；金额只来自有效明细，不维护组织资金账户。费用更正先作废旧记录，再建立关联新记录重新确认。

活动主状态、结果与报名开关独立。首次执行记录批准报名快照，执行结束固定负责人与任务承担者的反馈资格依据；资格仍需当前成员或公开身份校验。取消后保留此前真实反馈但不再收集评分，不把取消当正常完成。

归档检查未结任务、物资、问题、待审费用和已确认总结来源是否仍匹配；如果确认后来源变化，必须重新核对并确认。普通写入与归档争用同一活动锁，不能在归档后悄悄提交。重新打开不恢复报名或反馈入口，历史确认快照只追加，不能覆盖。

来源摘要只计算实际输入投影：相关活动事实、已确认方案、任务、报名、费用、执行记录和反馈，使用固定字段与稳定排序。排除本次总结内容及保存时间、AI 记录、通知、访问日志和归档操作自身的元数据，避免保存／确认总结就使自身来源失效；归档在同一短事务内重算并比较。

创建及重复处理按开发规范使用业务唯一键或持久防重记录；不自建通用状态机、规则引擎或统一软删除框架。各实体的可删除、取消、作废及保留历史规则分别实现。

## 六、文件、通知与 AI 外部动作

### 6.1 附件所有权与存储一致性

每个附件属于一个组织、一个活动及一个明确用途；若关联任务或费用，只能关联其中一个合法业务对象，不能用任意字符串表名来动态访问。公开活动不自动公开附件；任务承担者可处理本人任务允许的附件，管理者处理活动资料，普通成员不能上传票据。

上传先验证粗粒度权限，在受控临时目录完成大小、类型和内容检查，然后以新生成的不可变存储名移动到同一持久存储中的最终位置；文件成功落盘后，短事务按锁协议再次验证资源状态，再登记归属、防重结果和审计。禁止原始文件名决定路径，不在同源直接执行 HTML／SVG 等内容。

落盘后登记失败，只有核对不存在数据库引用时才清理本次新文件；提交结果未知先查询，不删除可能已提交的附件。进程在落盘与登记间中断会留下孤立文件，通过清单与保留期核对清理，不能删除已确认资料。重复上传的输家只清理本次生成且未引用的文件，不碰防重结果指向的既有附件。

允许删除的附件先在事务中标记不可访问并记录清理状态，再在提交后删除磁盘内容；磁盘删除失败保留重试依据，不恢复业务可见性。确认或仍被依赖的附件拒绝删除。数据库与文件不是同一事务，不宣称自动原子回滚。

下载、预览、删除重新鉴权；先取得一致的权限和文件元数据，再输出内容，不在整个传输期间持有数据库锁。已开始的下载无法撤回，后续请求按最新权限拒绝。文件不放容器临时层或公开静态目录。

### 6.2 站内提示的可靠来源

直接“提交后发通知”在进程中断时会丢失接收人，因此关键业务事务同时记录最小通知意图：来源操作、接收账号、类型及资源引用；以来源操作、接收账号、类型唯一防重，不复制完整敏感正文。

事务提交后尝试生成接收者提示；失败记录在意图状态中，主业务仍成功。首期使用 Spring 定时任务小批处理到期的未投递意图，有限退避及次数上限后保留失败供维护重放；批量与频率在实现时配置，不部署队列，也不建设通用消息平台。这是已有业务提示的恢复机制，不新增定时群发业务。意图登记失败意味着业务提交条件未满足，整体回滚；投递失败发生在提交后，不回滚，这是两个不同阶段。

取消、移交等动作的接收人按当次操作固定，不在补建时根据最新成员重新推算；列表及详情跳转再检查当前权限。公开报名者的变更提示不以“仍为组织成员”为前提。

### 6.3 AI 调用与人工确认

由 AiGenerationService 编排：短事务获取一致的授权输入与来源版本、记录请求；事务外使用当前组织已测试并启用的配置调用模型；短事务复核权限及活动状态、保存结果。输入只含所需数据，程序先计算人数、金额、比例；不开放工具调用、跨组织查询或模型写权限。

生成记录与业务文稿分离。客户端采用草稿后，方案保存走 activity、总结保存走 review，确认均需版本与来源匹配；AI Service 不直接写确认状态。归档或撤权发生后，结果可在受限生成记录中保留核对依据，但不能继续返回给已失权用户或写成有效业务文稿。

模型连接、整体时限、输入长度、并发和每日调用量都配置有界上限，具体值结合选定模型确定并记录。额度按持久生成记录计算，单实例并发门控只限制正在进行的调用，不为限流写完整分布式平台。未知计费结果不自动重试；重启后遗留生成中记录经超时核对转为明确结果，不无限挂起。

普通 HTTP 返回完整草稿，暂不做流式输出；模型失败使用统一错误码且保留人工内容。生成记录按原防重键进行只读状态查询，具体路径在 P8.1 接口说明中与生成入口一起定义；requestId 仅用于追踪单次 HTTP 请求，不能作为重复调用或结果恢复的唯一依据。查询与重放按开发规范再次鉴权。

### 6.4 可配置协议与密钥

业务入口与权限以计划书 7.4 为准，配置及测试归 modules/ai；组织设置页面承载该模块组件，不让 organization 保存另一份密钥。每组织最多一条当前配置，带 version、connectionRevision、测试通过版本与操作者记录；数据字段在 P8.1 迁移前落定。version 用于所有保存及启停的乐观锁；connectionRevision 只在协议、端点、模型、认证、密钥及调用参数变化时递增，测试成功绑定它。下文“当前版本的测试”均指 connectionRevision，单纯启用不使其刚通过的测试自行失效。

| 协议 | 请求与响应适配 |
| --- | --- |
| OPENAI_CHAT_COMPLETIONS | 完整 POST 端点；Authorization: Bearer；model、messages、stream=false，输出上限使用经目标模型验证的参数；取 choices 中的最终正文 |
| ANTHROPIC_MESSAGES | 完整 POST 端点；默认 x-api-key，anthropic-version 固定为适配器支持的版本；system 与 messages 分离，max_tokens 必填、stream=false；按顺序合并 content 中的 text 块 |

Anthropic 兼容网关若要求 Bearer，可在该协议的认证方式中明确选择，默认仍为 x-api-key；不开放任意请求头或任意 JSON 模板。只建立两种必要协议适配，共用 Java HTTP、超时、错误和文本结果结构；服务商名称只是显示信息，不据此分派业务。当前不支持 Responses、工具执行、图片、流式输出或模型自动发现。模型 ID 手工填写，不能硬编码仅允许某几个品牌。

仅发送基础文本所需参数，不默认强塞 temperature、推理开关等厂商差异参数。OpenAI 格式的输出上限字段允许选择 max_tokens 或 max_completion_tokens；通过本次真实测试确认支持情况，不在失败后自动换参数重发。忽略推理块和工具块；空正文、拒绝、非预期结构或截断返回明确结果，不把思考内容或不完整文本当作成功文稿。Anthropic 协议参考[官方 Messages 文档](https://platform.claude.com/docs/en/api/messages/create)。

**密钥存储：** API Key 仅从 HTTPS 表单一次提交到本系统后端，后端用标准 AES-GCM 加密保存，随机 nonce、认证标签及 keyId 一并管理，组织 ID 作为关联数据；主加密密钥由部署环境提供且不进库、不进仓库。密钥不能仅做散列，因为调用时需要解密。查询 DTO 只返回 hasApiKey，不返回原值或密文；日志、审计、错误和生成快照都不保留密钥。恢复时需单独安全保存对应主密钥；主密钥不可用时 AI 配置报错，允许重新配置，不影响手工业务。

**外部地址边界：** 完整端点仅允许 HTTPS、合法公网域名及部署允许的端口，禁止 userinfo、片段和携带密钥的 query；部署维护允许访问的域名清单，首期覆盖所支持厂商，新增可信网关时由部署配置扩充。拒绝回环、私网、链路本地及云元数据地址；测试与生成共用同一校验。不能只校验保存时的域名：连接时必须防止 DNS 重绑定，并通过受限出口或绑定已验证解析结果保障实际目标；若当前 HTTP 客户端无法保障，使用受限出口，不能声称一次 DNS 检查已足够。关闭重定向，禁止将密钥转发到另一个主机；不提供任意 URL 探测器。

**配置与测试：** 读取、保存、测试和启用均逐请求鉴权并受 CSRF 保护。保存校验 version；key 不传表示保留，替换必须传入新值，清除单独表达。地址或协议变化必须重输密钥且清除旧测试状态。测试针对已保存的指定版本，用固定非业务短文本和有界输出；限制频率、并发、响应体大小及总时限，计入组织调用额度，超时不自动重试。测试完成后再次核对负责人权限及配置版本，过期测试不能将新版本标为通过。启用仅接受当前版本的成功测试结果。

**在途调用：** 请求快照保留非敏感的协议、模型、配置版本及端点标识，不保存密钥。实际发出前再检查配置有效；结束时版本已变化或已停用则标记配置失效，不自动采用、不换用新配置补发。已返回的人工草稿不因停用而被删除。错误区分未配置、未启用、配置变更、上游认证失败、模型不支持、限流与超时；上游 401 不能映射为本系统账号失效，返回安全的 AI 错误码及 requestId。

## 七、数据库、配置与运行要求

业务记录使用明确关联和唯一约束：账号与组织成员主关系、活动与账号报名、活动与账号反馈、请求防重及通知意图分别唯一；退出后再加入更新原成员关系并保留历史，不允许生成多个有效身份。按组织、活动及实际列表条件设计必要索引，不给每列自动建索引。

迁移文件只定义已决定的结构；账号、邀请、恢复凭据和通知基础设施不直接等同于概念 ER 图中的实体数量。Java 时间使用明确的时区转换，数据库时间基准统一 UTC，日期字段与时间点分开。各表长度、金额容量和索引在该模块第一份迁移前确定。

数据设计与模块接口说明按开发规范第五节增量建立。P0 首先核对 JDK、Wrapper、兼容依赖、真实 MySQL 开发／测试环境以及 Flyway 可运行；不能用 UI 演示的构建代替后端联通，也不为探活新增业务表。测试库必须独立命名并在破坏性测试入口验证目标配置，禁止使用正式运行库执行清表或迁移重置。

配置使用类型化配置和启动校验：数据库、文件目录、会话、上传限制、模型开关和调用限额有明确来源；模型关闭或未配置时核心业务仍能启动，AI 入口返回服务未配置，不能加载假结果。组织配置无效时拒绝其 AI 操作，不阻止其他组织及核心业务启动；不静默使用占位密钥。

运行、异常和业务审计日志按开发规范，不单独实现 Controller 请求体全量日志切面。恢复码、模型输出、用户附件和完整反馈不能进入普通日志。维护接口不提供给普通业务账号，数据库连接使用最小必要权限。

备份在维护窗口暂停新写入，等待在途业务及上传登记完成，协调数据库与附件清单快照；在独立环境恢复检查，不能只核对压缩包存在。目标服务资源、备份保留值、文件限额和模型服务商尚需在部署／接入设计时落实，这些是运行参数，不重新打开框架选型。

## 八、验证与完成边界

构建与入口要求见开发规范。必须通过真实入口覆盖：多组织关联越权、成员撤权竞争、账号恢复后旧会话、申请截止后审核、最后名额、超预算并发确认、归档与写入竞争、反馈历史资格、通知投递中断、文件登记失败以及模型超时／撤权／幂等重放。

每项验证保留条件、操作和实际结果；READ COMMITTED、锁顺序与唯一约束都要在真实 MySQL 测试库检查。当前只完成文档设计，业务代码、安装组合、数据库迁移、性能与恢复均未运行，不能把框架能力当作本项目已经具有的保障。
