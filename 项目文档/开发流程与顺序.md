# 基于 Vue 的多组织活动管理系统设计与实现

## AI coding 开发流程与顺序

用途：规定先做什么、何时进入下一步、跨阶段依赖如何补齐，以及每次 AI coding 如何交付。本文不维护第二份完成清单，不包含工时或日历排期。

业务范围与权限以[项目计划书](项目计划书.md)为准；具体开发项和完成状态只维护在[功能开发清单](功能开发清单.md)。工程及开工条件引用[开发规范](开发规范.md)，目录与技术分别引用[前端架构](前端架构与技术栈设计.md)、[后端架构](后端架构与技术栈设计.md)，视觉实现引用[前端 UI 设计与规范](前端UI设计与规范.md)。本文只维护执行顺序与任务推进方法。

当前已推进到 P1.3 的阶段实现；先按[开发进度审核报告](开发进度审核报告.md)修复基础缺陷，完成 P1.4 当前资源授权检查，再进入 P2。根据功能清单及实际代码恢复，不重复初始化；下方 P0 顺序保留作首次建工程的流程说明。

## 一、执行原则

1. **一次完成一条可验证流程。** 默认一次任务选择一个小阶段，体量大时拆成可独立检查的小目标，例如“创建活动草稿并保存”，不使用“把所有后端写完”作为任务范围。
2. **先定当前合同，再实现当前流程。** 先明确本次字段、权限、状态和接口，再做迁移、服务、页面和联调；不预先设计全部表，也不让前后端各自猜字段。
3. **后端约束与前端体验一起交付。** 业务流程必须包含真实持久化、授权和必要异常；UI token、失焦校验、加载与错误反馈随本页面落实，不留到最后统一换皮。
4. **沿用已选架构。** 优先现有代码、标准能力和组件库，只封装已出现的共同职责。未实现模块不建空包、占位表、假接口或无效菜单。
5. **前置条件看能力，不看整章是否全勾选。** P0、P1 的部分条目依赖后续业务，可按第四节补齐；已经出现的越权或一致性问题必须修复，不能用“以后联动”推迟。
6. **用户指定范围决定本次终点。** 用户授权一个小阶段，就完成该阶段可落实的工作后汇报；授权连续多个阶段，则在通过阶段检查后继续，不逐步索要重复确认。未授权时不自动扩展成整个项目开发。

## 二、默认开发顺序

```text
P0.1 最小工程与环境
  → P0.2 首批 token／主题 + P0.3 最小传输／错误边界
  → P1.1 真实账号链路
  → P1.2 组织 → P1.3 成员 → P1.4 当前已有资源的授权
  → P2 活动草稿、人工方案、立项与变更
  → P3 附件、任务、物资
  → P4 报名、审核、取消、导出
  → P5 经费登记、确认与统计
  → P6 执行、取消、反馈、人工复盘、归档
  → P7 工作台与站内提示
  → P8 真实 AI 总结与方案
  → P9 综合验收、部署与恢复
```

这是个人开发的默认串行顺序。P4 在业务上不依赖全部 P3，但默认先完成筹备协作再做报名，减少上下文切换。调整先后时必须保留真实依赖，不改变功能清单的编号和范围。

### 2.1 P0：建立最小可运行基础

| 顺序／对应项 | 本步实施范围 | 进入下一步的证据 |
| --- | --- | --- |
| 1 · P0.1 | 核对当前仓库与环境，锁定兼容依赖，创建最小 frontend／backend、Wrapper、配置示例和独立 MySQL 开发／测试环境；验证连接、迁移机制及只读联通 | 正式前端可启动和构建；后端可构建并连接指定数据库；实际命令写回 README。业务写入验证随 P1.1 补齐 |
| 2 · P0.2 基础部分 | 建立 tokens.css、Element Plus 映射、base 样式与首批检查；使用首个实际页面需要的组件验证主题和弹层 | 无页面私有设计数值；首批组件及弹层主题生效；未实现菜单不展示 |
| 3 · P0.3 基础部分 | 最小 Fetch 入口、请求取消与错误对象、服务端参数校验、统一错误及安全日志；为首个账号流程准备 CSRF 和会话接入 | 能区分正常响应、204、字段错误和网络失败；不会重复提示或泄露内部错误；尚无业务权限时不设置假授权 |

P0.2 与 P0.3 可以围绕首个账号页面交替推进，不要求先完成全部基础设施。没有实际业务表时不创建探针业务表；没有附件接口时不先编写全套附件页面。原型构建不算正式工程通过。

### 2.2 P1：先账号，再组织与权限

| 顺序／对应项 | 本步实施范围 | 进入下一步的证据 |
| --- | --- | --- |
| 4 · P1.1 | 先补账号数据与接口合同；按 CSRF → 注册及恢复码发放 → 登录 → 当前身份 → 退出推进，再完成恢复、重新签发、认证版本与限流 | 账号真实入库且重启保留；登录／退出、失效、恢复及失败反馈可验证；旧响应不清除新登录。未来公开参与页面的回跳在 P4 补齐 |
| 5 · P1.2 | 组织创建、本人组织目录、组织工作区与切换；无组织账号保持可用 | 创建者身份正确；跨组织切换不会残留旧数据；当前可用页面按实际权限展示 |
| 6 · P1.3 | 邀请接受、成员列表、负责人授予／撤销及移交；落实当前成员变更事务 | 重复邀请接受不重复入组，并发变更不会移除最后负责人 |
| 7 · P1.4 基础部分 | 在已有组织资源上证明读取、写入、关联与撤权规则；定义后续活动职责接入点 | 越权请求被服务端拒绝，撤权与写入竞争有检查；不存在的活动／任务联动仍保持待完成 |

第一条账号链路只证明账号能力，不提前声称 M01 全部完成。组织、活动及附件陆续加入后，继续扩展同一授权入口，而不是各写一套权限判断。

### 2.3 P2—P5：建立活动并逐项接入业务

| 顺序／对应项 | 本步实施范围 | 进入下一步的证据 |
| --- | --- | --- |
| 8 · P2.1 | 活动数据合同、列表、详情与草稿创建／编辑；组织负责人指定活动负责人，详情只挂已实现区段 | 草稿持久化、字段校验与活动级隔离正确；普通成员看不到未发布内容 |
| 9 · P2.2 | 人工方案保存、提交、撤回、驳回和立项确认，保留确认记录 | 单负责人自行确认与多人审核均可用，冲突不重复生效；完全不依赖 AI |
| 10 · P2.3 | 筹备期关键变更、暂停发布／报名和重新确认；先覆盖已有数据规则 | 不把重新进入草稿误判为可删除初始草稿；报名及费用保护随 P4／P5 补齐后才能认定整项完成 |
| 11 · P3.1 | 先实现活动资料的受控上传、预览、下载、删除与失败恢复；任务／票据用途随相关记录接入 | 文件落盘与元数据可核对，越权和伪装文件被拒绝；统一传输与 CSRF 不被 Upload 绕过 |
| 12 · P3.2 | 任务创建、指派、本人状态推进、管理者取消／重新打开及历史，接入任务附件 | 成员仅处理本人任务；状态变化与完成时间一致；指派产生持久通知意图 |
| 13 · P3.3 | 本人任务、物资清单及状态；补齐任务／物资责任移交 | 任务与物资互不伪造状态；普通成员不能修改物资；退出不会留下悬空责任 |
| 14 · P4.1 | 公开活动页面、登录回跳与报名申请，补齐公开／本人页面布局 | 外部报名不自动入组；公开响应无内部字段；重复申请不产生第二条主记录 |
| 15 · P4.2 | 管理审核、报名开关、名额和审核时限 | 真实 MySQL 争抢最后名额只成功一次；截止后审核遵守计划书规则 |
| 16 · P4.3 | 本人结果与取消、管理取消、名单导出；补齐退出和关键变更的报名联动 | 同一 Web 系统在手机浏览器可完成报名、结果查询与取消；导出授权及文本安全正确；取消不重复释放名额。活动整体取消联动在 P6.2 完成 |
| 17 · P5.1 | 支出草稿、字段校验、无票说明及凭证用途；补齐 P3.1 的票据权限 | 金额精确传输及持久化，普通成员不能访问费用与票据 |
| 18 · P5.2 | 提交、确认、驳回、作废、更正及超支说明 | 重复和并发确认不重复累计；保存与确认权限分开 |
| 19 · P5.3 | 预算和支出统计；补齐关键变更时的已确认费用保护 | 零预算、超支、作废和更正可复算，统计与明细一致 |

每增加一种业务记录，就扩展对应组织退出、活动变更和资源授权检查。不能等到 P6 才首次发现已存在的任务或费用可以跨组织关联。

### 2.4 P6：先形成完整的人工闭环

| 顺序／对应项 | 本步实施范围 | 进入下一步的证据 |
| --- | --- | --- |
| 20 · P6.1 | 启动执行、报名接受快照、执行记录、结束及反馈资格依据 | 待审未结束不能执行；不生成到场记录；执行结束不自动完成任务 |
| 21 · P6.2 | 活动取消、报名与任务联动、物资及费用遗留处理、取消说明 | 取消不可恢复正常执行；重复取消不重复处理，历史与责任人保留 |
| 22 · P6.3 | 反馈提交／修改、本人及管理查看、平均评分 | 资格、唯一性和取消边界有效；首次归档后的关闭规则随 P6.5 联测 |
| 23 · P6.4 | 人工总结、改进说明、确认快照及来源失效判断 | 无 AI、无反馈也可完成复盘；来源变化后必须重新核对 |
| 24 · P6.5 | 正常／取消归档、只读、重新打开与再次确认；联测全部已有模块 | 归档与在途写入竞争正确；重开不恢复报名或反馈；此前跨阶段联动全部复核 |

到这里应能用同一场活动贯通人工流程。若核心业务仍依赖模拟数据、固定通过结果或跳过权限，则不能用工作台包装或 AI 功能掩盖缺口。

### 2.5 P7—P9：真实汇总、AI 与交付

| 顺序／对应项 | 本步实施范围 | 进入下一步的证据 |
| --- | --- | --- |
| 25 · P7.1 | 分身份工作台、本人待办与授权跳转 | 普通成员与管理者的数据范围不同；待办来自真实未处理记录 |
| 26 · P7.2 | 已定义 KPI、必要图表及明细追溯；按需接入 GSAP | 每个值可复算，无假增长曲线；token、手机和减少动效状态符合 UI 规范 |
| 27 · P7.3 | 基于前期通知意图完成投递、列表、跳转、失败补建与防重 | 中断和重复投递可恢复；固定接收人不丢失；撤权后提示不泄露资料 |
| 28 · P8.1 | 先做组织模型设置、密钥保护及两种兼容协议的连接测试，再做启用、限额、生成记录、状态查询及 AiDraftPanel | 原文保留，未知外部结果不盲重试；先与总结场景结合，不建无人调用的 AI 平台 |

| 30 · P8.3 | 在已有活动草稿接入方案生成与人工保存 | 假设与事实分开；不自动建任务、改预算或批准活动 |
| 31 · P8.4 | 两种协议及两项 AI 的正常、缺失、矛盾、诱导、失败、撤权、恶意地址及配置切换检查 | 真实调用证据与故障后人工路径均成立，不以模板冒充模型 |
| 32 · P9.1 | 同一活动贯通、多身份及特殊路径演示 | 按 A01—A20 映射核对，记录实际结果而非只看页面能打开 |
| 33 · P9.2 | 关键异常回归、手机和键盘、统计复算及实际环境下的数据检查 | 未解决问题有明确范围；权限、名额、金额等关键缺陷已消除 |
| 34 · P9.3 | 环境重建、部署、配套备份与独立恢复、文档和图示交付 | 源码与说明可复现，数据库及文件恢复可读；成果反映真实实现 |

工作台骨架和空状态可以提前随布局出现，但正式统计在真实业务数据具备后落实。两项 AI 都是本期交付内容，人工链路先完成不等于省略 AI。

## 三、每次 AI coding 的固定流程

### 3.1 接手与定范围

先读 README、AGENTS、本文及功能清单，再按当前任务读取计划书对应章节、开发规范和相关架构；涉及界面时读 UI 规范。接着检查实际代码、Git 改动和已有测试，确定已完成内容，避免覆盖用户改动或重复初始化。

用简短说明给出：本次目标、对应小阶段、前置能力、验收行为与涉及目录。缺失信息不影响当前工作时采用合理默认值；若影响权限、数据保留或外部操作，先澄清该项，继续其他独立且已授权工作。

### 3.2 补齐当前设计

按开发规范第五节，在首次需要时创建并更新数据设计和接口说明；只写本次涉及的表、字段、状态、接口与页面消费约定。先搜索已有组件、服务和查询，决定复用位置，不为了“统一”重新包装组件库。

接口合同和数据约束须在对应代码前明确。具体实现无需每个字段都单独请求用户批准；发现会扩大功能或改变业务权限的冲突时，不能自行用实现替代需求决定。

### 3.3 实现与联调

推荐局部顺序：

```text
当前字段／接口合同
  → 最小迁移及必要反例检查
  → 后端授权、业务服务、事务和接口
  → 前端接口函数、页面与组件
  → 真实前后端联调
  → 异常、权限、UI 状态验证
```

可按反馈交替修改前后端，不要求所有后端完成后才动页面。UI 展示允许在明确的测试场景使用样例，但生产页面必须使用真实接口；测试替身不能作为数据库并发、真实模型调用或端到端验收证据。

通知意图、审计、防重和版本检查跟随首次需要它们的业务写入落地。公共逻辑保持原架构的所有者，不在页面和模块内各复制一份。

### 3.4 验证、收尾与交接

1. 运行当前工程已有且与修改相关的检查；对应前端类型、lint、测试、UI 门禁和构建，以及后端 Wrapper verify 的合同见开发规范。命令不存在时先在对应基础阶段落实，不能声称执行成功。
2. 通过真实界面验证本次流程及相关加载、空、失败和权限状态；关键并发与持久化在独立真实数据库检查。失败后先修复，不靠禁用检查继续。
3. 检查本次差异、配置和未使用内容，避免提交凭据、构建产物及无关修改；是否提交或推送按当前用户授权执行，不将推送作为每一步的默认动作。
4. 只勾选实际完成的开发项；部分完成、待联动或未验证保持未勾选，并在原清单对应小阶段旁简记已实现范围、验证结果、待补项及下一步。不要在本文复制进度表。
5. 同步实际变化所属文档，运行文档检查；汇报结果、检查证据、剩余限制及下一步。完成当前授权范围后交回，不自动跨入新阶段。

## 四、跨阶段补齐规则

| 前期条目 | 允许暂缓的部分 | 最迟补齐节点 |
| --- | --- | --- |
| P0.1 | 首个真实业务写入与重启持久化验证 | P1.1 |
| P0.2 | 组织壳、公开参与壳、真实路由引导及页面状态 | 各壳首个页面；公开参与部分在 P4 |
| P0.3 | 活动级授权、附件传输、模块防重与具体状态错误 | 对应模块首个接口，不等到 P9 |
| P1.1 | 公开浏览后登录并返回原活动 | P4.1 |
| P1.4 | 活动职责、任务／物资移交、内部报名退出联动 | 分别随 P2、P3、P4 接入；P6 复核历史资格，P7 复核旧通知 |
| P2.3 | 已有报名、费用及其他筹备记录的关键变更保护 | 对应 P3—P5；不是可以延后执行的现存数据校验 |
| P3.1 | 任务附件与票据用途、确认后的保留规则 | P3.2、P5；归档竞争在 P6.5 联测 |
| P4.3 | 活动整体取消时的报名结果联动 | P6.2 |

补齐是回到原条目完成其剩余条件，不再创建一个同义功能。阶段存在待补项时，不宣称整阶段完成；但只要下一步所需能力已验证，可以继续授权范围内的开发。

## 五、阻碍、暂停与恢复

- **环境缺失：** 明确缺少的实例、配置或依赖，完成不依赖它的准备；无法连接 MySQL 时不以 mock 验收数据库约束，也不将环境问题改写为更换整套框架的理由。
- **检查失败：** 保留能复现问题的最小条件，修复后重跑相关检查；未知提交结果按既有恢复合同核对，不以新键重复执行。
- **额度或会话中断：** 在原功能清单对应位置留下当前范围、改动文件、已通过／未通过检查、运行服务及下一步；不写入密码、密钥或恢复码，不另建散落的临时计划文档。
- **恢复任务：** 先检查实际 Git 差异、文件和已有进程，再从未完成步骤继续；不能仅凭上次文字结论推断仍在运行，也不重复启动同端口服务或覆盖已有工程。
