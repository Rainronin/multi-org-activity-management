# 接口说明

本文对照当前Controller、DTO与Service维护实际合同，覆盖P1—P8端点；测试结论见[审核报告](开发进度审核报告.md)，不在本文保留过期待办。

用途：按开发规范第五节，在首个相关端点编码前记录方法、路径、字段、错误码、权限与恢复路径；按模块逐段增量维护，前后端共享同一份合同。路径、错误结构与传输约定以[开发规范](开发规范.md)第二节为唯一上位约定，本文不复制其规则，只登记模块字段与消费约定。

公共约定（全模块适用）：

- 路径或查询参数类型不匹配、数值溢出返回 400 `VALIDATION_FAILED`，`fieldErrors` 标明参数名，错误说明不回显原始值或转换异常；受保护端点仍先校验登录。
- 所有非安全方法必须携带 `X-CSRF-TOKEN`（匿名端点不豁免，开发规范 2.4）；CSRF 失败返回 403 `CSRF_INVALID`。
- 未登录访问受保护端点返回 401 `AUTH_REQUIRED`；登录失败与恢复失败统一返回 401 `AUTH_INVALID_CREDENTIALS`，不区分账号不存在与凭据错误。
- 会话绑定账号 `auth_version`：修改密码或恢复成功后版本 +1，旧会话请求一律 401 `AUTH_REQUIRED`；发起变更的当前会话由服务端更新绑定版本。
- 登录按账号+来源 IP 统计失败；恢复按连接来源 IP 统计全部尝试（每 5 分钟最多 10 次），不采信查询参数或客户端转发头。同一来源共享恢复额度，超限返回 429 `RATE_LIMITED` 并附 `Retry-After`（秒）。
- 响应 `Cache-Control: no-store` 适用于 CSRF、恢复及一切受保护 JSON。
- 2026-10-04 核对全部 Controller 输出标识：活动 `submittedBy/confirmedBy/summaryConfirmedBy`、执行记录 `recordedBy`、费用 `submittedBy/decidedBy`、任务／物资 `activityId`、报名／反馈 `accountId`、邀请 `createdBy`、配置 `testedBy`、生成 `adoptedBy` 均为字符串；尚未发生的动作保留 JSON `null`。领域与输入 DTO 的数字类型不因此改变，`version`、容量、次数及计数仍为数字。`ErrorContractTest` 覆盖真实响应的 13 个字符串、7 个空值及 5 个数字检查。
- 公共 HTTP client 在响应正文读取完成后才清理超时及取消监听。成功 JSON 解析失败、非 ProblemDetail 的错误正文均为传输错误 `INVALID_RESPONSE`；正文中断为 `NETWORK_ERROR`，超时／主动取消分别为 `REQUEST_TIMEOUT/REQUEST_ABORTED`，保留响应头 `X-Request-Id`。等待 CSRF 凭据期间主动取消的请求不再发送；有效 ProblemDetail 的状态、错误码与字段错误仍按原合同传递。
- 当前会话的 403 `CSRF_INVALID` 只作废内存凭据，下一次用户操作重新获取，不自动重放；旧会话代次的 403 不清除新凭据，也不触发登录失效。

## 账号模块（M01，P1.1）

| 端点 | 方法 | 请求 | 成功 | 主要错误 |
| --- | --- | --- | --- | --- |
| /api/auth/csrf | GET | - | 200 `{token, headerName}` | - |
| /api/auth/register | POST | JSON `{username, password}` | 201 `{id, username, recoveryCode}`；恢复码明文仅此一次返回 | 400 `VALIDATION_FAILED`（fieldErrors.username / fieldErrors.password）；409 `USERNAME_TAKEN`；429 `RATE_LIMITED` |
| /api/auth/login | POST | `application/x-www-form-urlencoded` `username`、`password` | 204（登录成功是 204 的明确例外） | 401 `AUTH_INVALID_CREDENTIALS`；403 `CSRF_INVALID`；429 `RATE_LIMITED` + `Retry-After` |
| /api/auth/me | GET | - | 200 `{id, username}`（id 为字符串） | 401 `AUTH_REQUIRED` |
| /api/auth/logout | POST | - | 204 | 403 `CSRF_INVALID` |
| /api/auth/recover | POST | JSON `{username, recoveryCode, newPassword}` | 200 `{recoveryCode}` 新恢复码明文仅此一次；同一事务：改密码、旧码 CONSUMED、发新码、auth_version+1 | 401 `AUTH_INVALID_CREDENTIALS`（不泄露账号或码状态）；429 `RATE_LIMITED` |
| /api/auth/recovery/reissue | POST | JSON `{currentPassword}`，需登录 | 200 `{recoveryCode}`；旧码 REVOKED、发新码 | 401 `AUTH_INVALID_CREDENTIALS`；401 `AUTH_REQUIRED` |
| /api/auth/password | POST | JSON `{currentPassword, newPassword}`，需登录 | 204；auth_version+1，旧会话失效 | 401 `AUTH_INVALID_CREDENTIALS`；400 `VALIDATION_FAILED` |

字段校验：`username` 3～32 位 `^[a-zA-Z0-9_]{3,32}$`；`password` 与 `newPassword` 8～72 位且同时包含字母与数字；恢复码格式为服务端发放的分段十六进制串，比较前忽略大小写与连字符、空格。

防重与结果恢复路径：注册重复提交以账号唯一约束兜底返回 409 `USERNAME_TAKEN`，不产生第二个账号；恢复码已消费后重放统一 401，结果丢失时用户以新密码登录后可重新签发，不引入额外防重表（开发规范 2.5 的幂等键要求自首个可能重复计费／建单的动作起适用）。

前端消费约定：

- 注册、恢复、改密、重签从整表校验开始锁定输入并拦截重复提交；账号改密／重签互斥，发送中不关闭或离开页面，迟到的账号结果核对原会话及组件存活。明确拒绝或请求结束后解除提交锁，失败保留输入，不自动重放。
- 注册、恢复、重签响应中的 `recoveryCode` 仅展示一次，界面要求用户勾选并确认已保存后才能离开；Esc／关闭按钮不能绕过，未确认的路由离开被阻止，刷新／关闭仅提供浏览器提示，不承诺强制阻止。不写入 localStorage、日志或 URL。
- 5xx、超时、网络中断或成功响应无法读取属于结果尚未确认：注册用本次账号密码登录核对，恢复用新密码登录，登录成功后可重签恢复码；改密先用新密码登录核对，再尝试原密码；重签提示旧码可能已失效，可保持登录手动重签并保存新码。这里的重签是明确替换旧码，不恢复原次响应明文，也不添加账号请求键或额外防重表；自然网络提交时序仍待整体验收。
- 登录页 401 就地显示，不触发全局登录跳转；受保护请求的 401 `AUTH_REQUIRED` 由会话层单飞处理，只引导一次登录且核对会话代次，旧响应不清除新登录。
- 登录校验前锁定输入与提交，等待时保留原路由并固定回跳；5xx／传输异常说明登录结果尚未确认，可由用户手动重试。登录 API 不论成功或响应未确认，结束时均作废内存 CSRF，下一次写入重新获取，避免服务端已轮换凭据后重试 403；不自动重放。
- 注册 409、恢复／改密凭据 401 仍为统一拒绝，但提示补充：此前写入结果未确认时，先用本次账号密码或新密码登录核对，不能仅凭重放拒绝断定此前没有成功；注册不直接引导另建账号，恢复不透露账号或恢复码状态。
- 切回标签页读取 `/api/auth/me` 也沿用上述失效处理；先卸载旧会话页面和受保护表单，再引导登录，草稿守卫不能阻止失效引导。重登保留原路径，不恢复未提交草稿；网络读取失败保留原会话与页面，不当作 401。
- `CSRF_INVALID` 时前端刷新 CSRF 凭据并提示重试，不自动重放写请求。
- 登录回跳参数仅允许站内相对路由。
- 退出请求失败时会话层作废 CSRF，并只读核对 `/api/auth/me`（最长 10 秒）；仅当前代次明确返回 401 `AUTH_REQUIRED` 才清理受保护状态。仍登录或核对失败时三个退出入口保留原页、提示再次退出，不自动重放；确认退出后账号／组织入口转登录页，公开入口原地更新。旧退出成功、失败及核对响应不能清理新登录；这里保护客户端响应，不承诺已发送请求在服务端的执行顺序。

## 组织模块（M01，P1.2）

权限：全部要求登录；组织详情仅有效成员可见，非成员一律 404 `RESOURCE_NOT_FOUND`（不泄露组织存在性）。角色只有 `OWNER`（组织负责人）与 `MEMBER`；负责人授予／撤销属 P1.3。

| 端点 | 方法 | 请求 | 成功 | 主要错误 |
| --- | --- | --- | --- | --- |
| /api/organizations | POST | JSON `{name, description?}`；可选 `Idempotency-Key`（去两端空白后 1～64 字符，正式页面必带） | 201 `{id, name, description, role, joinedAt}`；新建者为首位 OWNER，同键核对返回原组织、当前身份和原加入时间 | 400 `VALIDATION_FAILED`；409 `IDEMPOTENCY_KEY_REUSED`／`REQUEST_IN_PROGRESS`；404 `RESOURCE_NOT_FOUND`（原组织当前不可访问） |
| /api/me/organizations | GET | - | 200 `{items: [{id, name, role, joinedAt}]}`（本人有效成员关系，按加入时间升序） | 401 `AUTH_REQUIRED` |
| /api/organizations/{orgId} | GET | - | 200 `{id, name, description, role, memberCount, createdAt}`（role 为本人角色） | 404 `RESOURCE_NOT_FOUND`（非成员或不存在的组织同一响应） |

字段校验：`name` 1～64 字符（服务端 trim）；`description` ≤512 字符可空。

防重与结果恢复路径（V22）：组织名仍可重复，但同一创建账号的请求键唯一；同键同名称／简介返回原组织，不重复建立成员关系或写创建审计，异内容 409。原账号在原组织须仍为有效成员，核对使用当前角色及数据库中的原 `joinedAt`；成员已移除时 404，不重放旧 OWNER 视图。并发唯一键冲突 409 `REQUEST_IN_PROGRESS`，保留原键核对；不同账号的相同键互不影响。旧无键调用继续兼容，但不保证防重。已复现“真实写入后页面收到替换的 503，重试产生两组织”，故原按钮禁用豁免不再沿用。

正式创建弹窗固定原键和原内容；网络异常、409 或 5xx 保留待核对状态、冻结表单并提供“核对创建结果”。明确 400／403／404／422／429 拒绝后可编辑；关闭或离开时保护未保存及待核对内容，发送期间禁止离开。取消提示保留原请求，确认放弃后先核对组织目录，避免重复创建。

前端消费约定：

- 当前组织由 URL（`/org/:orgId/...`）决定，不写入服务端会话、不作为授权依据；store 中组织目录按 orgId 索引，不保存可写的 currentOrgId。
- 组织切换：切换路由即切换数据作用域；页面请求全部携带 orgId 并在响应返回时核对归属，迟到响应不渲染；切换前如出现未保存内容按统一未保存提示处理（首次出现真实编辑场景时引入 useUnsavedChanges）。
- 非成员访问组织详情返回 404 时展示"组织不存在或无权访问"，不区分两种原因。
- 切回标签页时，组织布局读取当前 `GET /api/organizations/{orgId}` 并强制刷新 `GET /api/me/organizations`，核对请求序号与会话代次。角色变化清除并重新加载子页权限、草稿及配置；角色不变保留未保存内容。组织 404 清除子页与旧目录选择，不清账号或其他组织身份；网络失败保留草稿并提供“重新核对权限”。活动详情另重读活动，失去管理职责清除管理草稿，403／404 清除活动；权限不变或网络失败保留内容。任务／物资及“我的任务”重读当前职责，已开任务资料弹窗按最新任务授权显示上传。此机制无即时撤权推送，后端仍逐请求校验。

**执行记录防重（V21）：** 请求键在组织内唯一。重放必须为原操作者、同活动、同类型和去两端空白后的相同内容，并重新通过当前管理授权；成功返回原记录，不重复写审计。异内容、异活动或异操作者返回 `IDEMPOTENCY_KEY_REUSED`，并发唯一键冲突返回 `REQUEST_IN_PROGRESS`，须保留原键核对。归档后仅允许已存在的原键核对，不允许新增；旧无键调用继续追加，兼容但不保证防重。正式页面结果未知时固定键和内容、冻结输入并显示“核对记录结果”，取消离开保留原请求；确认离开提示先核对记录列表，避免另起新请求。

**普通活动编辑边界：** `PATCH /api/organizations/{orgId}/activities/{activityId}` 仅允许草稿按既有字段规则修改，筹备中仍仅允许组织负责人修改简介；待确认、执行、复盘、取消及归档状态返回 409 `ACTIVITY_STATE_CONFLICT`。执行后的实际更正走执行记录，重新打开后仍遵循所处状态规则。

**物资写入边界：** 新增、编辑和状态流转统一在组织及活动锁内检查 `isPreparationWritable()`；筹备、执行与复盘可维护，初始草稿、待确认、调整期待确认、取消和归档只读，拒绝返回 409 `ACTIVITY_STATE_CONFLICT`。

**票据下载边界：** 通用附件下载端点遇到 `EXPENSE_VOUCHER` 时，与费用凭证列表一样要求组织负责人或该活动负责人；其他成员返回 404，不泄露票据是否存在。普通活动及任务资料仍按原活动可见性读取。

**只读边界（P6.5）：** 归档后任务、物资、附件、费用与执行记录全部拒绝新增或修改；执行记录及费用原键核对仅返回已有记录，并重验当前权限／原请求归属。已确认或已作废费用的凭证不可删除；归档资料删除需先由组织负责人重新打开活动。

**总结来源摘要（P6.4）：** 确认时保存固定字段、稳定排序的摘要，覆盖活动事实及说明／负责人／方案／取消理由，任务与物资id／version，全部报名id／状态，全部费用id／version，执行记录数，以及反馈id／评分／正文指纹。仅改任务、物资、费用正文或同评分反馈文字也会失效；归档锁内重算，不一致返回409 `ARCHIVE_BLOCKED`（detail含「来源已变化」）。Activity响应新增布尔`summaryNeedsReview`：复盘／取消且已确认时比较当前来源，页面提示重新核对；重新确认后false，归档历史不误标当前失效。新算法不回写旧sourceHash；旧已确认记录可能需人工再次确认，原正文快照保留，不伪造来源历史。

### 7.1 组织模型配置（只有组织负责人可写）

| 端点 | 方法 | 请求 | 成功 | 失败 |
| --- | --- | --- | --- | --- |
| /api/organizations/{orgId}/ai/config | GET | - | 200 配置视图；负责人得全部字段，其他有效成员只得 `viewerRole=MEMBER`、`available`、`availableHint`、`configState`、`protocol`、`model`、`hasApiKey` | 404（非有效成员） |
| …/ai/config | PUT | JSON `{protocol, endpoint, model, authScheme?, apiKey?, clearApiKey?, maxOutputTokens, outputLimitField, timeoutSeconds, version?}` | 200 保存；首次保存不带 `version`，之后必须与读取值一致 | 400 `VALIDATION_FAILED`／`AI_ENDPOINT_REJECTED`；403（非负责人）；409 `EDIT_CONFLICT` |
| …/ai/config/test | POST | JSON `{version}`＋可选`Idempotency-Key`（正式页面必带原键） | 200 `{status, message, testedRevision, requestId, testedAt, errorCode}`；原键返回原测试结果，首次仅固定短文本并计入组织额度 | 403；409 `IDEMPOTENCY_KEY_REUSED`／`REQUEST_IN_PROGRESS`／`AI_NOT_CONFIGURED`／`AI_KEY_MISSING`／`AI_CONFIG_CHANGED`；502／504（见7.3） |

| …/ai/config/enable | POST | JSON `{version}` | 200 `enabled=true` | 403；409 `AI_TEST_REQUIRED`（当前修订未通过测试）／`AI_KEY_MISSING`／`EDIT_CONFLICT` |
| …/ai/config/disable | POST | JSON `{version}` | 200 `enabled=false`，保留配置与已返回草稿 | 403；409 `EDIT_CONFLICT` |
| …/ai/config/clear-key | POST | JSON `{version}` | 200 清除密钥、同时停用、`connectionRevision` 递增、测试状态清空 | 403；409 `EDIT_CONFLICT` |

- `protocol` 只允许 `OPENAI_CHAT_COMPLETIONS｜ANTHROPIC_MESSAGES`；`endpoint` 是**完整** POST 端点（不自动拼接 `/v1` 等路径）；`model` 手工填写；`authScheme` 只允许 `BEARER｜X_API_KEY`（OpenAI 固定 Bearer，Anthropic 默认 `X_API_KEY`，兼容网关可显式选 Bearer）；`outputLimitField` 只允许 `MAX_TOKENS｜MAX_COMPLETION_TOKENS`；`maxOutputTokens` 64～4096；`timeoutSeconds` 5～60。
- 密钥：`apiKey` 不传且未明确清除时保留，传新值表示替换；正式页面通过 `clear-key` 清除。旧兼容保存请求也支持 `clearApiKey=true`，同一次 UPDATE 原子清空密文及主密钥标识、停用、递增连接修订并清空测试状态；版本只递增一次。不能同时提供新密钥与清除标志（400）。查询只返回 `hasApiKey`，不回显原值与密文。修改 `protocol` 或 `endpoint` 必须重新输入密钥（400），避免把旧密钥静默发送到新地址。
- `version` 是所有保存与启停的乐观锁；`connectionRevision` 只在协议、端点、模型、认证、密钥与调用参数变化时递增，递增时清空旧测试状态并置 `enabled=false`，需重新测试才能启用；单纯启用不使刚通过的测试失效。
- 主密钥由部署环境提供（`ACTIVITY_AI_MASTER_KEY`，Base64 的 32 字节 AES 密钥，不进库不进仓库）；未提供或无法解密时 AI 配置返回 503 `AI_KEY_UNAVAILABLE`，手工业务不受影响。
- 配置操作互斥并捕获原组织、会话、配置版本与原键。连接测试RUNNING、UNKNOWN、传输失败及查询404保留原意图并冻结配置，仅GET核对，不自动POST；UNKNOWN包括超时、连接失败、上游5xx及中断，不能宣称厂商未处理。已经完成的无效输出等FAILED允许用户明确确认另一次测试，新意图用新键。初次无键旧调用仍兼容，但不具有同键恢复保证。后端在组织共享锁后首次读取角色／配置，排队后读取当前事实，再事务外调用模型。

方案生成条件（`conditions`）：`topic`≤200、`goal`≤500、`audience`≤200、`expectedParticipants` 1～100000、`budget`≤200、`timePlace`≤200、`constraints`≤500；至少填写主题或目标，未填写项由模型标注“假设”或“待补充”。

生成编排（后端架构 6.3）：短事务取授权输入与来源版本并写请求记录 → **事务外**调用模型 → 短事务复核权限、活动状态与配置修订后保存结果。

- 权限：方案生成与手工保存方案一致（仅活动草稿期、组织负责人或活动负责人，未发布活动对他人 404）；总结生成与手工总结一致（复盘期或取消后的遗留处理期且未归档）。非成员 404，其他成员 403。
- 防重：同组织、同操作者、同 `Idempotency-Key` 且内容相同只调用一次模型并返回既有记录；内容不同返回 409 `IDEMPOTENCY_KEY_REUSED`；并发首次提交撞唯一键返回 409 `REQUEST_IN_PROGRESS`。页面结果未知时保留原键与生成条件，通过 `by-request-key` 只读核对（`RUNNING` 稍后再查）；核对失败仍保留原键，不自动再次调用模型。重放与查询均重新鉴权，不返回撤权前的草稿（F01 口径）。
- 输入：只发送本次生成必需的信息（活动事实、已确认方案、任务、报名汇总、执行记录、已确认费用与反馈要点），排除联系方式、账号凭据、通知与访问日志；人数、金额与比例由程序先算好再交给模型；资料统一放在定界块（`【资料开始】…【资料结束】`／`【条件开始】…【条件结束】`）中，系统提示声明块内文字只是资料，诱导指令不改变任务、权限或触发操作。
- 输出：只取最终正文（忽略推理块与工具块）；空正文、拒绝、非法结构、截断与超长都返回明确错误，不当作成功草稿；输出按纯文本入库，前端只按文本显示，不执行其中的 HTML 或脚本。
- 结果：调用期间配置被修改或停用返回 409 `AI_CONFIG_CHANGED`（不自动采用、不换用新配置补发，已产生的文本只保留在受限生成记录中作为核对依据）；调用期间撤权或活动状态变化返回原鉴权错误并把记录标为 `AI_PERMISSION_REVOKED`；遗留 `RUNNING` 记录在超过时限后的查询／生成时转为 `FAILED`（`AI_CALL_ABORTED`），不无限挂起。
- 采用：`adopt` 只写采用状态；方案保存仍走 `PUT …/proposal`，总结保存与确认仍走 `PUT …/summary` 与 `…/summary/confirm`，版本与来源校验不变；归档后不再生成总结。
- 页面生成请求保存后捕获同一响应式对象，首次 201／SUCCEEDED 直接展示草稿，不误要求额外核对；未知结果仍按原键查询。采用固定发起时的生成记录，响应只在当前记录和会话仍匹配时回填；新一轮生成期间返回的旧采用状态及业务错误不替换新记录或人工文本，真正 401 仍按原会话代次处理。旧采用已写入不承诺回滚，无新增端点或自动调用。

| OpenAI Chat Completions | `Authorization: Bearer` | `model`、`messages`（system＋user）、`stream=false`、`max_tokens` 或 `max_completion_tokens`；取 `choices[0].message.content`（兼容分段数组） |
| Anthropic Messages | 默认 `x-api-key`（兼容网关可选 Bearer）＋ `anthropic-version: 2023-06-01` | `model`、`max_tokens` 必填、`system` 与 `messages` 分离、`stream=false`；按顺序合并 `content` 中的 `text` 块 |

不支持 Responses、工具执行、图片、流式输出与模型自动发现；不在失败后自动更换参数重发（`max_tokens` 与 `max_completion_tokens` 由本次真实测试确认）。
