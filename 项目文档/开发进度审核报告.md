## 二、当前问题与修复要求

### F01 · 高：外部参与者没有可用的报名与取消流程（P4／S11）

[PublicActivityDetailPage.vue](../基于Vue3的多组织活动管理系统_zcode/frontend/src/features/activity/PublicActivityDetailPage.vue) 的 goApply 在已登录时只跳转 `/`，正文明确要求进入组织工作区报名。实际报名组件 RegistrationPanel 位于内部活动页，依赖 orgId、成员身份与组织详情权限。

**本轮实测：未加入任何组织的账号点击“进入工作区报名”后落在账号页，没有报名表单。** 同账号直接调用公开活动报名 API 可以得到 PENDING，说明阻断在前端流程。随后账号页“我的报名”没有活动名称、详情链接或取消按钮，只显示报名展示名、状态和时间；API 也不返回活动安排与调整提示。见[外部账号截图](../验证截图/DS审核-外部账号.png)。

现有 audit_p4_ui.mjs 先把测试账号加入组织，再进入内部页报名，只覆盖“组织成员报名公开活动”，不能证明外部参与闭环。

修复：登录后留在公开活动上下文直接申请；本人报名入口展示对应活动、安排、处理原因及允许的取消操作，支持活动撤回时仍读本人状态与调整提示。复用已有申请／取消 API，不能要求外部参与者入组。补完全无组织账号的登录回跳→申请→结果→取消检查。

### F02 · 高：重新提交后冻结失效，调整期附件仍可删除（S07／S09）

[Activity.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/activity/Activity.java) 的 isPendingReconfirmation 只判断 DRAFT 且 confirmedAt 非空，遗漏重新提交后的 PENDING_APPROVAL。任务、物资、附件上传依赖该判断；附件 delete 完全没有调整期判断。

**实测：已确认→撤回→重新提交待确认后，创建任务返回 201；撤回 DRAFT 时删除已有附件返回 204。** 另外，从未确认的初始草稿创建任务也返回 201，说明当前仅排除特定调整状态，没有实现计划书“筹备／执行时创建任务”的正向约束。

修复：按操作允许的状态约束完整生命周期，调整期覆盖草稿及待确认，上传／删除／编辑／状态推进都受控。附件确认／引用保留不能全部推迟到 P6。对两个调整状态及首次确认前分别验证，不能只测撤回瞬间。

### F03 · 高：调整期离组不会取消内部报名（S07-B）

[RegistrationMapper.xml](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/resources/mapper/registration/RegistrationMapper.xml) 的 listBlockingForLeave 限制 `a.status = 'APPROVED'`。原已通过报名在活动撤回 DRAFT 或重新提交 PENDING_APPROVAL 时不被选中，因此成员离组会跳过取消，留下有效报名及名额。

这是 SQL 与 OrganizationMemberService 调用链静态确认，本轮未单独新增离组时间交叉测试；已有正常筹备期退出实测通过不覆盖该分支。计划书允许调整期合法退出，须覆盖尚未进入执行的内部活动，而非仅 APPROVED；未来开始时间与实际执行状态也应分别遵守合同。

### F04 · 高：共同锁协议没有完整实现，锁前授权仍会过期（S08）

[TaskService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/task/TaskService.java) 的 requireWriteContext 先读取成员和活动、生成 Context，再取活动共享锁，之后继续使用旧 Context；没有组织行锁。[MaterialService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/material/MaterialService.java) 同样先授权与状态检查，再加活动共享锁，也没有组织锁。

影响：等待活动锁期间发生撤回／改派后，旧请求仍可能使用旧状态或角色写入；成员撤权／退出与任务分派未遵守同一组织锁，不能保证退出职责检查与分派一致。这是代码路径确认，本轮未注入该并发时序，不能写成“实测已发生越权”。

修复：相关写入口按约定锁顺序取锁，在锁内重新读取当前身份、活动和目标记录再判断。活动自身方案保存、提交、确认等也要逐入口核对，不能仅看存在 lockActivity 方法就认定协议完成。跨模块编排目前在 OrganizationMemberService 且直接写报名／通知，已不只是“只读 Mapper 依赖”；按架构统一实现位置或明确最小合理例外，不能用错误注释掩盖依赖。

### F05 · 高：省略版本可覆盖编辑，方案和审批未受旧版本保护（S08）

[ActivityMapper.xml](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/resources/mapper/activity/ActivityMapper.xml) 的 updateDraft 仅在 version 非空时追加条件，相关请求没有强制版本；任务／物资编辑存在同类可选判断。saveProposal／updateProposal 没有期望版本参数，状态动作也只检查源状态，不能识别同状态反复流转后的旧审批。

**实测：PATCH 不传 version 返回 200；方案保存携带过期 version=0 仍返回 200并写入内容。** 带旧版本字段编辑的现有测试通过，只能证明条件存在，不能证明无法绕过。

修复：编辑及需要冲突识别的动作按开发规范强制版本或等价前置条件；前端实际携带，方案保存与审批纳入同一合同。补缺版本、过期方案、撤回重提后的旧审批反例。

### F06 · 中：创建防重绑定可变内容，编辑后同键重试失败（S08）

ActivityService.sameCreationContent 将重放请求与当前 activity 字段比较，而非首次创建的稳定输入。记录被编辑后，原请求就会被误判不同内容。

**实测：首次创建后修改地点，原键＋原请求重放返回 409。** 本轮重跑已有 audit_p234_recheck.mjs，其 replaySameKey 也输出 409／sameId=false，但脚本仍退出 0；原“同键同内容返回原资源”的完成声明不可靠。

修复：保留不可变的创建请求指纹或等价最小依据；对同键并发创建还需处理唯一约束冲突后的结果恢复，不能返回 500。附件上传仍没有规范要求的防重键／结果核对入口，也不能计为创建防重全覆盖。

### F07 · 高：附件登记使用锁前任务身份，改派后仍可能上传（S09／S10）

[AttachmentController.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/attachment/AttachmentController.java) 在 stage 前通过 taskOwner 读取 Task 并封装；同一对象传给 register。[AttachmentService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/attachment/AttachmentService.java) 锁内虽然重读组织成员与活动，却用旧 OfTask.task.assigneeMemberId 判任务承担者，没有重读并保护当前任务。

若上传落盘期间发生改派，旧承担者可能凭旧对象登记文件。本轮为静态时序分析，未执行延迟上传／改派竞争；需要针对两阶段间改派的回归测试。修复时在登记事务中按当前任务重新验证，并与任务改派使用相容锁协议。仅重读活动不能替代任务授权。

附件删除改为提交后清磁盘是有效改进；进程中断后的文件核对、类型深层校验及确认／引用限制仍未完整验收。本轮还实测中文文件名被重复 URL 编码，Content-Disposition 中出现 `%25E5...`，应由框架仅编码一次。

### F08 · 中：通知来源和本人调整提示仍缺，不能全部归入 P7（S11）

RegistrationService 的批准、驳回、本人／管理取消只写审计，没有通知意图；ActivityService 的重新确认也没有给既有报名者记录变更来源。只有任务分派、退出报名部分路径已有 notification 写入。

按功能清单，P7 可以后做提示列表／投递，但来源意图必须随当前业务同事务产生。本人记录没有活动安排、调整标识，F01 实测也确认这些字段缺失。应区分当前就要补的来源／结果数据与 P7 才展示的通知界面。

### F09 · 中：管理名单只显示前 20 条，无翻页；导出会静默截断

RegistrationPanel.loadAll 只保存 page.items，丢弃 total，没有页码控件；fetchActivityRegistrations 不接收页码，后端默认 pageSize=20。同状态超过 20 条时，后续申请无法从此页审核。

RegistrationService.exportForReview 固定查询前 5000 行，注释说超限提示缩小范围，但没有总数判断或提示，导出成功会悄悄丢失后续记录。两项为静态确认；本轮未造 5001 条数据。补分页及导出超限反馈即可，不需批处理框架。

### F10 · 中：当前文档互相矛盾，验收场景覆盖不足（S12）

原接手摘要一处称 P4 前端已完成未提交，另一处称未完成；任务附件既在完成表又在待办。报告混合多轮“未提交／未修复／已关闭”，不能作为新 AI 的可靠上下文。本次已用当前快照替换，历史留开发日志和 Git。

现有 70 项后端测试与 14 项前端测试通过，但前端测试仍仅 HTTP／会话；公开报名浏览器脚本使用组织成员、观察脚本对关键输出不作断言，遗漏上述故障。DS 所称逐段关闭守卫实验本轮未重做，不把自述当成本轮独立证据。

## 三、产品与 UI 判断

- **公开信息仅包含 PUBLIC 活动是正确边界**，无需把内部活动放入匿名列表。错误在于公开参与的登录后操作被送进内部工作区，不是公开筛选规则。
- **调整期已有任务承担者的读取需要明确一致策略**：当前活动任务端点按未发布规则 404，但本人任务列表直接查询任务，没有同样活动过滤。这既不支持统一“调整期只读”，也不是所有入口都 404。建议保留本人既有任务只读及调整提示，并避免泄露未确认活动新字段；作为待落实的产品规则，不能擅自扩大到所有成员可见完整草稿。
- 本轮检查了真实 P3／报名详情页 1440／1024／768／390／320 宽度：**页面级无横向溢出**，无 pageerror。320 宽下长表需横向浏览，见[截图](../验证截图/DS审核-320宽.png)。这仅是布局抽查，不代表已完成五档上传、编辑、审核、导出、键盘、短屏和 200% 缩放验收。
- PublicActivityDetailPage／PublicActivitiesPage 仍有 220px／320px 栅格宽度硬编码，报名表单没有完整失焦校验配置；check:ui 通过没有覆盖所有规范。按既有 token／Element Plus 规则收尾，不另换设计。
