## 2. 需修复的问题

以下“高优先级”应在 P2 前处理；“中优先级”应在本轮基础收尾完成，不能用修改规范来掩盖实现缺口。

### R01 · 高：并发接受邀请会返回 500

证据：[OrganizationInvitationService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/organization/OrganizationInvitationService.java) 的 `accept` 先普通读取邀请，再锁组织；当前配置未设置架构规定的 READ COMMITTED，本机 MySQL 查询为 REPEATABLE-READ。在真实测试库预先短暂持有组织锁，同时让同一账号发送两次接受请求，实测状态为 **200、500**。

原因：两个事务在锁之前建立旧读取视图；后一个获得锁后，普通成员查询仍可能读不到前一个新成员。唯一键阻止重复入组，但异常分支的普通查询仍使用旧视图，最终抛出异常。数据没重复不等于幂等交互正确。

修复：落实后端架构 5.1 的隔离级别与锁内当前状态读取；重复接受应返回已有关系，不重复扣次。保留真实 MySQL 并发检查，覆盖同账号重复接受、不同账号争抢最后次数、撤销与接受竞争。不能只捕获所有数据库异常并返回成功。

### R02 · 高：会话代次保护实际缺失，失效后旧目录能重新出现

证据：[session.ts](../基于Vue3的多组织活动管理系统_zcode/frontend/src/stores/session.ts)、[organizations.ts](../基于Vue3的多组织活动管理系统_zcode/frontend/src/stores/organizations.ts)。`observeUnauthorized` 只看当前是否 authenticated，没有请求所属会话代次；`bootstrap` 也无代次保护；组织目录请求返回后直接覆盖 store。

浏览器内定向控制响应实测：清空目录后释放旧响应，旧账号目录重新写回；当前身份已认证时交付旧 401，状态变为 guest；401 处理后目录仍未清空。清单所写“代次检查”与代码不符。

修复：在会话边界维护代次，读取与错误副作用都核对发起时的代次；会话失效统一清理受保护缓存与 CSRF，阻止旧请求回填。补充登录 A → 旧请求挂起 → 登录 B → 旧成功／401 返回的检查。切回标签页重新验证会话及当前组织的规范也尚未落实，需要一起补齐。

### R03 · 高：成员页沿用旧组织数据，失权后没有完整清理

证据：[OrgMembersPage.vue](../基于Vue3的多组织活动管理系统_zcode/frontend/src/features/organization/OrgMembersPage.vue) 仅 `onMounted(loadMembers)`，没有监听 orgId、响应序号或清理旧成员；[OrganizationLayout.vue](../基于Vue3的多组织活动管理系统_zcode/frontend/src/layouts/OrganizationLayout.vue) 未按组织授权状态限制子页面显示。

实测通过 Vue Router 从甲组织 members 路由切到乙组织 members 路由，组织标题已为乙，表格仍显示仅属于甲的成员。常规侧栏切换目前先跳概览，因此单测一次侧栏切换会漏掉这个问题。404 等失败路径也没有清空已加载成员；确认框中的写操作直到确认时才读取当前 orgId，存在旧目标与新组织上下文混用。

修复：读取随路由范围重建，核对 orgId、请求序号与会话代次；失权清理本组织数据，刷新目录；写操作固定发起时的组织与目标，切页时取消尚未提交的确认。增加同路由参数变化、快速来回切换和撤权后的检查。

### R04 · 高：创建／撤销邀请遗漏组织锁，授权检查可能被撤权穿过

证据：[OrganizationInvitationService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/organization/OrganizationInvitationService.java) 的 `create`、`revoke` 只调用 `requireOwner`，未获取组织锁；接口说明却声明所有变更均在组织排他锁内完成。这一项是代码路径审核结论，本次未做并发撤权复现。

负责人通过校验后，另一事务可能先完成撤权，旧请求随后仍写入邀请。修复时按既定锁协议在锁内重新验证身份，创建／撤销与成员撤权必须使用兼容的组织锁顺序；用真实两事务测试证明撤权生效边界。

### R05 · 中：重新入组的成员主关系与架构不一致

证据：[V3__organization.sql](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/resources/db/migration/V3__organization.sql) 只约束有效关系唯一；`accept` 每次重新入组均 INSERT。实测退出／移除后再接受邀请，memberId 发生变化。后端架构第七节明确要求更新原成员主关系并另保留历史，数据设计却把两种方案留待决定。

这会影响后续活动职责、任务及历史署名如何关联。应在 P2 引入这些外键前收敛为既定主关系模型；新增迁移处理已有数据，不修改已应用的 V3。实际还允许被移除者使用原有未失效邀请码再次加入，与界面“需要新的邀请”不符；多次邀请码的撤销及再加入语义须明确，不能只改提示掩盖权限预期。

### R06 · 中：手机成员页严重溢出，token 门禁存在漏检

证据：[OrgMembersPage.vue](../基于Vue3的多组织活动管理系统_zcode/frontend/src/features/organization/OrgMembersPage.vue) 的标题与操作栏没有小屏重排，表格列宽直接写 `180/140/260`；[check-ui.mjs](../基于Vue3的多组织活动管理系统_zcode/frontend/scripts/check-ui.mjs) 未检查这类 props。

真实浏览器 390 CSS 像素视口实测页面 scrollWidth 为 **509—540**（不同测试账号文本下），标题被挤成竖排，页面整体横向溢出。截图：[手机](../验证截图/审核-P13-手机.png)、[桌面](../验证截图/审核-P13-桌面.png)。截图为本机验证产物，按项目规则不入库。

修复：按集中布局 token 让标题／按钮区在小屏重排，约束主内容收缩，横向滚动仅留在表格区域；列宽等设计 props 消费 token。桌面展开／折叠及真实 390 视口重新对照 Demo。静态门禁通过不能证明页面符合规范。

### R07 · 中：接口合同与已交付入口尚未闭环

- 接口说明承诺重复移除返回 204；实际第二次返回 **404**，现有测试还把 404 当作预期。应统一已授权操作者的重复处理语义，同时保留对无权用户的资源隐藏。
- 邀请列表／撤销已有后端和 API 函数，成员页没有使用它们；负责人创建一次性展示的邀请码后无法在界面管理或撤销。不能仅称作无影响增强，应补上必要的已发邀请管理入口。
- 成员列表目前整批返回，无查询参数；清单“必要的查询”缺少对应界面和接口。应依据已有分页合同完成当前需要的查询，或明确小规模列表的适用边界，不能默默视为全部完成。

对应文件：[接口说明](接口说明.md)、[OrganizationMemberService.java](../基于Vue3的多组织活动管理系统_zcode/backend/src/main/java/com/example/activity/modules/organization/OrganizationMemberService.java)、[organization/api.ts](../基于Vue3的多组织活动管理系统_zcode/frontend/src/features/organization/api.ts)。

### R08 · 中：本地配置进入构建包，测试配置不够可复现

本次 `verify` 生成的 JAR 实际包含 `BOOT-INF/classes/application-local.yml`。该文件虽被 Git 忽略，但 Maven 默认复制主资源目录，因此本地凭据仍可随构建包分发。修复应将敏感配置移到外部，或明确排除打包；发布前检查归档条目，无需读取或传播密钥。

测试依赖不入库的 `src/test/resources/application-local.yml`；所有测试采用 local profile，只有单个 DatabaseSmokeTest 在测试方法中检查 URL。它不能保证其他写测试或 Flyway 启动前一定阻止误连开发库。应提供可提交的不含凭据的测试配置入口，并在迁移和写入前验证精确测试库目标；凭据继续由外部注入。

### R09 · 中：文档当前状态与验证口径不同步

AGENTS、README、架构和流程仍含“尚无工程／全部待开发／从 P0.1 开始”，与提交和代码矛盾；功能清单同时声称已完成代次保护、手机无溢出等。实际前端只剩 **10 个 HTTP 单元测试**，没有会话／组织状态测试；后端 25 项中成员管理 6 项都是顺序操作，不能证明并发保证。

本次已更新现役入口、标明原文档审核为历史阶段记录，并撤回存在明确缺口的相关勾选。阶段历史留在开发日志；当前状态以清单和本报告为准。

## 3. 其他已发现的基础规范差异

本轮未扩展成全项目安全或性能审计。后续修复应同时核对这些已有代码路径：

- RequestIdFilter 沿用客户端 X-Request-Id，而开发规范要求服务端生成；登录失败日志直接插入未经控制字符处理的 username。需按既定日志规范修正。
- HTTP client 在收到响应头时就清除超时和取消监听，响应体读取不再受其保护；已取消的 signal 也未在订阅前判断。相关正文超时／预先取消检查缺失。
- 负责人移交、撤销后成员表会刷新，但侧栏组织角色和目录摘要没有同步刷新。实际权限由后端校验保障，界面仍可能显示旧身份。
