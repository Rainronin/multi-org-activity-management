CH 02

先建立全景图：浏览器、前端、后端到底谁在哪

这一章解释"前后端分离"和"单页应用（SPA）"这两个最基础也最容易含糊的概念。

三个东西，三个位置

单页应用（SPA）是什么

老式网站每点一个链接，浏览器就向服务器"要一张新网页"；而这个项目是单页应用：浏览器只从 Vite 拿一次"空壳"页面（index.html + 一堆 JS），之后切换页面（登录页 → 工作台 → 活动详情）都是 JavaScript 在浏览器里就地替换内容，地址栏变了但并不重新下载整页。只有数据需要随时找后端要，要来的都是 JSON 文本。

/api 前缀和"代理"

前端代码里所有请求都发往 /api/… 这种相对路径——没有写 http://127.0.0.1:8080。是因为 Vite 在开发时代理转发：见 vite.config.ts：

frontend/vite.config.ts
server: {
  host: '127.0.0.1',
  port: 5174,
  strictPort: true,              // 端口被占用直接报错，不悄悄换端口
  proxy: {
    '/api': { target: 'http://127.0.0.1:8080' },  // /api 开头的请求转给后端
  },
}
为什么要代理？浏览器有"同源策略"：页面只能向自己的来源发请求，否则会被拦（这就是 CORS 问题的由来）。让 Vite 替前端"传话"给 8080，页面就始终只跟 5174 说话，开发期绕开了 CORS，也统一了请求入口。

所以开发时要同时开着两个东西：后端（8080）和前端（5174）。浏览器打开的永远是 http://127.0.0.1:5174。

写法意思例子里的作用

第二段：逻辑（script setup）——怎么行为

frontend/src/features/account/LoginPage.vue（节选）
<script setup lang="ts">
import { reactive, ref } from 'vue'
import { useSessionStore } from '../../stores/session'

const session = useSessionStore()   // 拿到全局"会话仓库"
const router = useRouter()           // 拿到路由器，之后可以跳转

const formRef = ref<FormInstance>()  // ref：一个"响应式"的值，改它页面就变
const submitting = ref(false)       // 是否正在提交 → 控制按钮转圈
const errorMessage = ref('')        // 错误文案 → 控制红字显隐
const fields = reactive({ username: '', password: '' })  // 整个表单的数据

async function submit() {
  const valid = await formRef.value?.validate().catch(() => false)  // 先本地校验
  if (!valid) return
  submitting.value = true            // 注意：ref 要用 .value 读写
  try {
    await session.login(fields.username, fields.password)  // 发请求（第 08 章）
    await router.replace(safeNext())                       // 成功 → 跳走
  } catch (error) {
    if (error instanceof ApiError && error.code === 'RATE_LIMITED') {
      errorMessage.value = '登录尝试过于频繁，请稍后再试。'
    } else if (error instanceof ApiError && !error.isTransportError) {
      errorMessage.value = '账号或密码不正确。'            // 业务错误给具体提示
    } else {
      errorMessage.value = '网络连接失败，请检查网络后重试。' // 网络错误另说
    }
  } finally {
    submitting.value = false          // 无论成败都停止转圈
  }
}
</script>

记住三个核心词：

  • ref / reactive：把普通变量变成"响应式"——一旦修改，用到它的页面部分自动更新。这是 Vue 最核心的魔法（下一章专门讲原理）。ref 包单个值（脚本里读写要 .value），reactive 包对象。
  • <script setup>：组合式 API 的写法。顶部 import 进来的组件（ElForm 等）模板里直接用；这里声明的变量和函数模板里也直接可用，不用写 export default 那一大坨。
  • async/await：发网络请求要等，await 表示"等这一步出结果再往下走"；try/catch/finally 负责"成了怎么办、败了怎么办、最后一定做什么"。
第三段 style scoped：本项目每个页面样式都加了 scoped，意思是这段 CSS 只作用于本组件（Vue 会给元素加随机属性标记），不会污染别的页面。项目的颜色、字号等数值不自己写死，统一从 src/styles/tokens.css 的 CSS 变量取（第 12 章讲）。
CH 07

从"操作 DOM"到"声明式渲染"

这一章解释 Vue 最核心的机制：为什么改一个变量，页面会自己变？理解它，后面所有代码都会突然变得"理所当然"。

两种世界观的对比

设想一个需求：点击按钮，计数加一并显示。先看"手动操作页面"的传统写法：

// 传统写法：命令式，手动操作页面
const btn = document.querySelector('#btn')
const out = document.querySelector('#out')
let count = 0

btn.addEventListener('click', () => {
  count = count + 1
  out.textContent = String(count)  // 数据变了，还得自己改页面
})

原生 JS：数据和页面两本账

<span>{{ count }}</span>
<button @click="count++">加一</button>

<script setup>
import { ref } from 'vue'
const count = ref(0)
</script>

// 数据变了，页面自动跟着变，
// 不存在"忘了更新页面"这种 bug

Vue：声明式，只管数据这本账

Vue 的做法叫声明式渲染：你只声明"页面长什么样取决于哪些数据"，剩下的同步工作框架替你做。这消除了前端一大类经典 bug——"数据改了但界面没刷新"。

它背后做了什么（不需要会实现，理解方向即可）

可以把 ref 想成一份带订阅功能的公告：模板里用到 count 的地方，都在渲染时"订阅"了它；当 count.value 被修改，Vue 立刻通知所有订阅者"数据变了"，重新计算页面该长什么样，只把真正变化的部分更新到浏览器 DOM 上。这就是"响应式系统"：状态是因，视图是果，你只改状态。

最容易踩的坑：ref 在模板里直接写名字，在 JS 代码里必须 .value：submitting.value = true。忘了 .value 是初学者最高频的错误——代码不报错但页面不动。看别人的代码时先留意这一点。

computed 与 watch：响应式的两个延伸

  • computed 计算属性：由其他响应式数据"算出来"的值，依赖不变就缓存结果。真实例子：OrganizationLayout 里 const pageTitle = computed(() => route.meta.title ?? '组织概览')——路由变了标题自动变。
  • watch 侦听器："当某数据变化时，替我执行一个副作用"（发请求、关弹窗）。真实例子：登录后的布局里 watch(() => route.fullPath, closeMobileNav)——手机上点导航跳转后自动收起抽屉菜单。

经验法则：派生数据用 computed，做事情用 watch。分不清时先问自己：我要的是"一个值"还是"一个动作"？

逃生舱：模板引用（template ref）

绝大多数时候不需要手动碰页面元素，但表单组件库要求"调用组件的方法"（如触发校验），这时用 ref 拿到组件实例本身：

LoginPage.vue / ActivitiesPage.vue 的共同模式
const formRef = ref<FormInstance>()   // 模板里 <ElForm ref="formRef">

// 之后就能调用组件暴露的方法：
await formRef.value?.validate()          // 触发整表校验
formRef.value?.clearValidate()           // 清空校验红字

这是"声明式世界里少量命令式的逃生舱"，本项目只在表单校验这类场景使用，用完即止。

路由守卫：全局的"门禁"

frontend/src/router/index.ts（节选）
router.beforeEach(async (to) => {           // 每次跳转前都会先经过这里
  const session = useSessionStore()
  if (session.status === 'unknown') {       // 刚打开网页，还不知道登没登录
    try { await session.bootstrap() }       // → 问一次后端 /api/auth/me
    catch { return true }                    // 网络失败≠没登录，放行让页面自己报错
  }
  if (!to.meta.public && session.status !== 'authenticated') {
    return { path: '/login', query: { next: to.fullPath } }  // 未登录 → 踢到登录页并记下目的地
  }
  if (to.name === 'login' && session.status === 'authenticated') {
    return { path: '/' }                      // 已登录还访问登录页 → 直接送回首页
  }
  return true                                // true = 放行
})

meta: { public: true } 就是"此路免登录"的标记：登录、注册、找回账号和公开活动页有这个标记，其余页面都要过登录检查。这就是为什么你直接在地址栏输入 /org/1/members 而没登录时，会被自动送到登录页、登录后又回到原处——?next= 参数在起作用（登录页里的 safeNext() 函数还专门防了"外部网址钓鱼跳转"）。

支柱二 · 状态管理：数据放在哪

这一章回答一个高频疑问："哪些数据放全局，哪些放页面里？"

Pinia：全局"公告栏"

一个 store 就是一块全局公告栏：任何页面都能读、都能贴，一处更新处处可见。本项目只有两块公告栏，刻意克制：

  • stores/session.ts —— 会话：当前登录状态（unknown / authenticated / guest）、当前账号是谁。
  • stores/organizations.ts —— 我加入的组织目录（只存摘要列表）。
frontend/src/stores/organizations.ts（完整 37 行，有删节注释）
export const useOrganizationsStore = defineStore('organizations', () => {
  const items = ref([])          // 组织目录列表
  const loaded = ref(false)      // 是否已加载过（避免重复请求）

  async function fetchDirectory(force = false) {
    if (loaded.value && !force) return      // 已有数据就不重复请求
    const session = useSessionStore()
    const gen = session.capture()           // 记下"我是哪个会话期间发的请求"
    const responseItems = await fetchMyOrganizations()
    if (gen !== session.generation) return  // 期间登录身份变过 → 这份迟到的旧响应作废
    items.value = responseItems
    loaded.value = true
  }
  function clear() { items.value = []; loaded.value = false }
})

状态归属口诀

本项目（《前端架构与技术栈设计》5.1）把数据按"住址"分了四类，这比"全都塞进全局"高明得多：

住址住什么例子
Pinia（公告栏）真正跨页面共享的身份类状态登录状态、账号、组织目录
URL（地址栏）可以分享、刷新不丢的东西当前组织 orgId、活动 activityId、页码
页面组件（自己家）只属于本页的临时状态表单内容、弹窗开关、当前列表数据
后端（真身）一切权威数据权限、名额、金额——前端只是展示，不做第二套判断
为什么"当前组织"存在 URL 而不存 store？因为存 store 会出真问题：开两个浏览器标签页分别切到不同组织，共享的那份"当前组织"会互相覆盖，A 标签页可能拿到 B 组织的数据。URL 天然每个标签页一份，刷新、分享链接也不丢。这就是架构文档说的"路由是当前页面组织的唯一来源"。

活动列表、任务列表这些"页面级数据"也都不进 Pinia——它们住在各自页面组件里（第 16 章会看到完整实现）。判断标准很简单：两三个互不相干的页面都要读同一份数据，才配进 store。

支柱三 · 网络请求：全项目只有一扇门

这一章看懂 shared/http/client.ts 的封装思路——这是本项目工程化的起点。

如果每个页面都自己写 fetch，很快就会出现：有的忘了超时、有的错误提示五花八门、有的漏了安全头。所以项目规定：业务代码不准直接用 fetch，一律走 request()：

frontend/src/shared/http/client.ts（节选）
export async function request<T>(path: string, options: ClientRequest = {})
    : Promise<ClientResponse<T>> {
  const method = options.method ?? 'GET'
  const headers = await resolveHeaders(options, method)
  // ↑ 非查询类请求（POST 等）会自动附加 CSRF 安全头，防跨站伪造请求

  let response: Response
  try {
    response = await fetch(path, {
      method, headers,
      body: options.json !== undefined ? JSON.stringify(options.json) : …,
      signal: timeoutController.signal,   // 超时/取消都靠这个信号
      credentials: 'same-origin',         // 记得带上会话 Cookie
    })
  } catch (cause) {
    if (timedOut) throw new ApiError({ kind: 'transport', code: 'REQUEST_TIMEOUT', … })
    throw new ApiError({ kind: 'transport', code: 'NETWORK_ERROR', … })
  }

  if (!response.ok) {                     // 4xx/5xx：后端给了结构化错误
    const problem = toProblemDetail(await parseJsonBody(response))
    throw new ApiError({ kind: 'server', status: response.status,
      code: problem?.code ?? …, detail: problem?.detail ?? …,
      fieldErrors: problem?.fieldErrors ?? [] })
  }
  return { status: response.status, headers: response.headers, data: await response.json() }
}

错误分两类，页面对号入座

  • 传输错误（kind: 'transport'）：断网、超时、被取消——跟你的操作对错无关，统一提示"检查网络"。
  • 业务错误（kind: 'server'）：后端明确拒绝，带状态码和错误码（如 RATE_LIMITED、AUTH_REQUIRED），还可能带字段级错误（"用户名已存在"指到具体输入框）。

第 06 章 LoginPage 的 catch 里那句 error.isTransportError 分支就是在区分这两类。全部业务请求都长一个样——比如账号模块的 api.ts：

frontend/src/features/account/api.ts（节选）
/** 登录为表单编码（开发规范 2.4）；成功 204 无响应体。 */
export async function login(username: string, password: string): Promise<void> {
  await request('/api/auth/login', {
    method: 'POST',
    form: new URLSearchParams({ username, password }),
    response: 'none',          // 不需要读响应体
  })
}

防重复提交：幂等键

"提交"类请求还有一层保护：shared/http/idempotency.ts 里的 newIdempotencyKey() 生成一个一次性编号随请求发给后端。设想"点创建 → 网络断了 → 不知道成没成功 → 只能重试"的场景：如果没有编号，重试会再创建一条；带上同一个键，后端能认出"这是刚才那次请求"，不会重复处理。第 17 章会在创建活动的完整流程里看到它怎么用。

CSRF 是什么，一句话版：浏览器会自动带 Cookie，恶意网站就能"借你的登录身份"偷偷发请求。CSRF Token 相当于每封"写操作信件"里夹的一张防伪码，后端验过才受理。本项目由会话层"单飞"获取（并发时只发一次请求），client 只负责夹带——两层职责分离，见 stores/session.ts 顶部注释。

  • 首次加载（骨架屏，和真实表格同形状，不会闪一下）

这一章解决"组件之间怎么说话"——这是读和写组件的第二项基本功。

原则先记住一句话：数据经 props 向下传，事件经 emit 向上报。子组件永远不直接改父组件的数据。

完整案例：组织切换器（props + emit）

OrganizationSwitcher.vue 是侧栏里的组织下拉框，麻雀虽小五脏俱全：

frontend/src/features/organization/OrganizationSwitcher.vue（完整逻辑段）
const props = defineProps<{
  organizations: OrganizationDirectoryItem[]   // 父传：组织列表（只读！）
  modelValue: string                           // 父传：当前选中的 orgId
}>()

const emit = defineEmits<{
  change: [orgId: string]                      // 子上报：用户想切到哪个组织
}>()

const current = computed(() =>
  props.organizations.find((org) => org.id === props.modelValue))

function onChange(orgId: string): void {
  if (orgId && orgId !== props.modelValue) {
    emit('change', orgId)   // 只"发通知"，自己不切组织
  }
}

注意最后一句的分工：切换器只发出"我想切换"这个事件，真正改 URL、清数据由父层（布局壳）决定。组件源码注释里写着"切换只发出事件，导航由布局协调"——组件保持"傻"，职责越清晰越好复用。

生命周期、侦听器与 Composable

这一章讲"时间维度的代码"：组件出生、活着、销毁时分别该做什么，以及如何把逻辑打包复用。

组件的一生（够用的版本）

  1. 1setup 阶段<script setup> 的顶层代码

    初始化响应式变量、声明函数。此时页面还没渲染出来，不要在这里发请求。

  2. 2onMounted：已挂载onMounted(() => { … })

  3. 3活着：watch 在值班watch / computed

Composable：把"带状态的一段逻辑"打包带走

如果几处都要"延迟出现骨架屏"的逻辑，复制粘贴会腐烂。Vue 的做法是写一个 composable（以 use 开头的函数），把响应式状态 + 操作函数 + 清理逻辑打成一个包。项目里最好的例子是骨架屏节流：

frontend/src/shared/utils/useLoadingSkeleton.ts（节选）
export function useLoadingSkeleton() {
  const loading = ref(false)
  let leadingTimer: ReturnType<typeof setTimeout> | undefined
  let trailingTimer: ReturnType<typeof setTimeout> | undefined

  /** 开始一次首次加载：领先延迟后才显示骨架，很快结束就完全不显示。 */
  function begin(): void {
    clearTimers()
    leadingTimer = setTimeout(() => { loading.value = true; shownAt.value = Date.now() }, leading)
  }

  /** 请求结束：骨架已出现时补足最小停留时间（trailing），避免"闪一帧"。 */
  function end(): void { /* …补足最小停留后 loading.value = false… */ }

  // 组件销毁时自动清掉定时器——清理逻辑内置，调用方不用操心
  onScopeDispose(clearTimers)

  return { loading, begin, end, hide }
}

它解决一个真实的体验问题：本地接口经常几十毫秒就返回，如果"请求一发出就显示骨架"，骨架会闪一下反而难看。所以：leading 延迟（很快结束就压根不显示）+ trailing 保底（显示了就至少停留一瞬）。ListPage 内部调用它（配合 watch(loading, …, { immediate: true })），所有列表页白得这份体验。

命名规则：带响应式状态、要绑组件生命周期的复用逻辑才叫 useXxx；纯工具函数（如读 token 数值的 readUiToken.ts）就放 utils/ 用普通名字。这是架构文档明文规定的区分。

/** 将集中定义的 px 长度交给要求数值的组件；其他 CSS 值直接在样式中消费。 */
export function readUiLength(name: `--ui-${string}`): number {
  const value = getComputedStyle(document.documentElement).getPropertyValue(name).trim()
  if (!/^\d+(?:\.\d+)?px$/.test(value)) {
    throw new Error(`设计 token ${name} 必须是有效的 px 长度`)
  }
  return Number.parseFloat(value)
}

传 '--ui-control-height' 合法；传 'margin' 直接编译报错。类型本身就是一份"能自动执行的文档"。

export function toProblemDetail(value: unknown): ProblemDetail | null {
  if (typeof value !== 'object' || value === null) return null
  if (typeof record.status !== 'number') return null   // 字段真的存在吗？
  // fieldErrors 还要逐项确认 field/message 是字符串…
}
答辩金句："TypeScript 声明不能验证网络数据，所以对分页结构、状态值等关键字段保留运行时检查；但也不为简单接口搭通用 schema 引擎。"——这是《前端架构与技术栈设计》第六节的原话，背下来比写十个 interface 更值钱。

第二层：加载函数与三重守卫

ActivitiesPage.vue 的 loadActivities（节选）
let requestSeq = 0

async function loadActivities(): Promise<void> {
  const seq = ++requestSeq              // 守卫①：本次请求的"号码牌"
  const targetOrgId = orgId.value       // 守卫②：记住为哪个组织而发
  const gen = session.capture()         // 守卫③：记住哪个登录会话期间发的

  // 四态的关键分支：没数据才走骨架屏，有数据只提示"更新中"
  if (items.value.length > 0) refreshing.value = true
  else loading.value = true

  try {
    const [result, organization] = await Promise.all([
      fetchActivities(targetOrgId, { page: page.value, query: …, status: … }),
      fetchOrganization(targetOrgId),        // 顺带确认我的角色
    ])
    // 三个守卫有一个对不上，说明结果已经"过时"，直接丢弃：
    if (seq !== requestSeq || targetOrgId !== orgId.value || gen !== session.generation) {
      return
    }
    items.value = result.items
    total.value = result.total
    amOwner.value = organization.role === 'OWNER'
  } catch (error) { /* 同样的守卫检查 + observeUnauthorized + 分错误类型写 errorText */ }
  finally {
    if (seq === requestSeq) { loading.value = false; refreshing.value = false; loadedOnce.value = true }
  }
}

三重守卫各防一种事故：seq 防"连点搜索，慢的旧结果覆盖新结果"；targetOrgId 防"切了组织，旧组织的活动显示在新组织页面里"；gen 防"退出登录后，旧会话的响应又把数据填回来"。这就是架构文档 5.2 节"请求竞争"的落地。

第三层：组织切换 = 状态重建

第 09 章埋的伏笔在这里收尾——watch(orgId) 里把十来个状态逐一归零再重新加载。因为组件被路由复用了，"新页面"的一切都必须从新 URL 重建：页码回 1、筛选清空、四态回初始、弹窗关闭、作废旧请求序号。少清一个状态，就是一个跨组织串数据的 bug。

数据流总结：URL（orgId/页码/筛选）是输入 → 页面状态是从输入重建的产物 → 四态由 ListPage 统一表达 → 权限（amOwner）以接口结果为准。页面自己不发明任何"权威判断"。

catch (error) {
  if (error instanceof ApiError && !error.isTransportError) {
    // 明确拒绝（400/403/404/422/429）：后端没收下，清掉待存内容，用户可修改后重试
    if ([400, 403, 404, 422, 429].includes(error.status)) {

  }
}

区分"明确失败"和"结果未知"是这里面的灵魂：前者允许改了重交（新意图、新键），后者必须沿用原键原内容重试，由后端幂等去重。一句给用户的提示文案背后，是一整套一致性设计。

响应式布局与移动端适配

这一章揭示本项目最漂亮的一处 CSS 架构：断点决策全部集中在 tokens.css，组件一行媒体查询都不写。

核心思路：媒体查询只改变量，组件只消费变量

常见做法是在每个组件里写 @media (max-width: 768px)，后果是断点散落各处、改一个断点要全局搜索。本项目把断点当成集中设计决策（tokens.css 原注释），媒体查询里改的全是 CSS 变量：

/* 断点也是集中设计决策；不要把这些查询再复制到业务页面。 */

  :root { --ui-layout-kpi-columns: repeat(2, minmax(0, 1fr)); }  // 工作台 KPI 4 列 → 2 列
}
@media (width <= 700px) {
  :root {
    --ui-layout-main-offset: 0px;                    // 侧栏不再占位，内容全宽
    --ui-font-size-page-title: 1.5rem;               // 大标题缩小
    --ui-control-height: var(--ui-control-min-touch); // 控件加高到触控标准
    --ui-layout-login-columns: minmax(0, 1fr);       // 登录页从左右分栏变上下堆叠
  }
}

两处体贴的细节

测接口调用时，用 mock 替掉全局 fetch，让测试不依赖真实后端：

const fetchMock = vi.fn<typeof fetch>()

beforeEach(() => {
  fetchMock.mockReset()
  vi.stubGlobal('fetch', fetchMock)         // 全世界的 fetch 都换成假的
})

it('启动执行携带期望版本，缺失版本由后端拒绝', async () => {
  fetchMock.mockResolvedValue(jsonResponse({ status: 'EXECUTING' }))
  await startExecution('7', '10', 3)
  const init = fetchMock.mock.calls[0]?.[1] as RequestInit
  expect(String(init.body)).toContain('"version":3')   // 断言真的把版本号发出去
})

这个测试的名字本身就是文档："缺失版本由后端拒绝"——它在防"并发编辑互相覆盖"的问题，前端必须在启动执行时带上期望版本号。

项目测了什么，没测什么

有测试（.spec.ts）测的是
lifecycle / registrations / expense / workbench / ai各模块的纯业务逻辑与状态口径
session.spec.ts会话代次、迟到 401 不清掉新登录等高难并发场景
client.spec.ts统一请求入口：超时、取消、错误翻译、204 处理
没测像素级样式（由 check:ui 静态门禁 + 人工走查兜底）、跨组织权限（由后端数据库测试证明）
为什么业务规则写成 lifecycle.ts 这种纯函数文件？因为它不碰组件、不碰网络，输入输出一目了然——最容易测的代码就是最好的结构信号。"可测性"是这段代码的设计动机之一，答辩可以这么讲。

CH 26

术语表

被哪个词卡住就查哪个，按拼音/字母排序。

SPA（单页应用）

浏览器只加载一次页面外壳，之后的"换页"由 JS 就地替换内容完成。本项目就是 SPA，页面切换由 Vue Router 负责。

组件（Component）

可复用的页面零件，一个 .vue 文件就是一个组件：模板管长相、脚本管行为、样式管外观。页面也是组件（被路由挂载的大组件）。

组合式 API（Composition API）

Vue 3 推荐的组件写法：<script setup> 里直接声明变量和函数，按功能组织代码，而不是按选项（data/methods）分堆。本项目统一用它。

ref / reactive / computed

响应式工具：ref 包一个值（脚本中用 .value 读写），reactive 包一个对象，computed 是"由其他值算出来的值"且自动缓存。改了源头，页面自动更新。

声明式渲染

只声明"页面长什么样取决于哪些数据"，数据到页面的同步由框架完成；与之相对的是手动操作 DOM 的命令式写法（第 07 章有对比）。

生命周期钩子

组件在"出生（setup）→ 挂载（onMounted）→ 销毁前（onBeforeUnmount）"等时刻自动调用的函数，用来安排"什么时候发请求、什么时候清理"。

v-model

双向绑定语法糖：表单输入与变量实时同步。等价于"绑定 value + 监听 input 事件"两件事。

props / emit / 插槽

组件的三种对外交涉：props 是父传子的"入参"，emit 是子向父"发通知"，插槽是把"一段模板"塞进子组件预留位置（AuthLayout 的 <slot/>、ListPage 的 #actions/#filters）。

Composable（组合式函数）

把"响应式状态 + 操作 + 清理"打包的 useXxx 函数，如 useLoadingSkeleton。纯工具函数不放这个命名空间。

懒加载（Lazy Loading）

用到时才下载代码。本项目路由全部写成 () => import(...)，首次打开只加载登录页需要的 JS。

路由守卫（Navigation Guard）

路由跳转前的统一关卡，本项目用 router.beforeEach 实现"未登录不许进"和"登录后不再看登录页"。

布局壳（Layout）

带导航栏/侧栏的"外壳组件"，子页面渲染在壳的 <RouterView/> 里。本项目有 Auth、Public、Organization 三个壳。

Pinia / Store

官方状态管理库；一个 store 是一块跨页面共享的全局数据。本项目只有 session 和 organizations 两个 store，刻意克制。

单一数据源

一份数据只有一个"权威住址"，别的都是引用。本项目：当前组织住 URL；权限以后端为准；设计数值住 tokens.css。

CSRF

跨站请求伪造攻击：恶意网站借你浏览器里的 Cookie 冒充你发请求。防御是写操作必须带一张后端发的防伪 Token。见 client.ts 的 CSRF 头注入。

幂等键（Idempotency Key）

写请求附带的一次性编号：网络重试时沿用同一个键，后端能识别"这是同一次意图"，不会重复创建。见 idempotency.ts 和创建活动流程。

代理（Proxy）/ 同源策略 / CORS

浏览器规定页面只能向"同源"地址发请求；开发期由 Vite 把 /api 转发给 8080，让前端始终同源，绕开跨域（CORS）限制。

REST / API / JSON

后端把能力开放成一个个 URL 端点（如 POST /api/activities），请求和响应的数据格式是 JSON 文本。接口清单在《项目文档/接口说明.md》。

HTTP 状态码

200 成功有数据；204 成功无内容（登录就返回它）；401 未登录/会话过期；403 已登录但无权限；404 资源不存在。前端对不同码给出不同处理。

TypeScript / 严格模式

JS 的超集，给变量、函数、接口标类型，写错在编译期就报错。本项目 strict 全开，接口响应都定义了类型（如 MeResponse）。

设计 Token / 断点

集中定义的 CSS 变量（颜色/间距/字号/断点），全项目只准消费 token 不准写死数值。响应式断点也住在 tokens.css，媒体查询只改变量值（第 18 章）。

骨架屏（Skeleton）

加载中的灰色占位形状，和真实内容同构，减少"白屏突兀感"。本项目用 leading/trailing 延迟防止骨架闪烁。

竞态 / 迟到响应

快速连续操作时，先发的请求可能后回来，旧数据覆盖新数据。本项目用"请求序号 + 会话代次"丢弃过期的迟到响应（见 session.ts、OrganizationLayout.vue）。

单飞（Single-flight）

并发触发同一件事时只真正执行一次，大家共享结果。CSRF 凭据的获取就是这样：十个人同时要，只发一次请求。

四态列表

列表面板的四种互斥状态：失败 / 首次加载（骨架）/ 空 / 有数据。由共享组件 ListPage.vue 统一管理，杜绝"骨架和空态同时出现"。

Mock / Stub / 断言 / 回归

测试词汇：mock/stub 是"用假对象替掉真实依赖"（如替掉 fetch）；断言（expect）是"实际结果必须等于期望"；回归（regression）指"修好的 bug 又出现"——测试就是防回归的保险。

DevTools

浏览器开发者工具（F12）：Network 看请求、Console 看报错、Elements 看结构样式、Application 看存储。第 21 章有面向本项目的使用手册。

CH 27

答辩加分点：这套代码里值得主动讲的亮点

这一章挑选几个超出入门水平的设计，每个都能展开成答辩里的一段"技术亮点陈述"。

  1. 会话代次（generation）防迟到响应 —— stores/session.ts。问题：旧会话发出的慢请求，可能在新用户登录后才回来，把新会话的数据覆盖掉。方案：每个请求登记发起时的"代次号"，响应回来时号对不上就作废。这是并发编程思想在前端的落地。
  2. 请求序号防列表竞态 —— ActivitiesPage.vue 的 requestSeq、OrganizationLayout.vue 的 directoryRequestId。问题：快速切换组织或筛选，慢的旧响应晚到会显示错数据。方案：只接受"最新一次发起"的响应。
  3. 传输错误与业务错误分家 —— shared/http/error.ts。断网和"密码错误"是两种性质完全不同的失败，提示语、重试策略都应不同。全项目一个 ApiError 类型统一承载，页面按 isTransportError 分流。
  4. 幂等键与"结果未知"处理 —— idempotency.ts + 创建活动流程。网络中断时区分"明确失败可重填"和"结果未知先核对"，后者沿用原键重试防止重复创建。这是分布式一致性的入门案例。
  5. CSRF 单飞 + 职责分层 —— client 不认识 store（不能反向依赖），凭据由会话层"并发只取一次"地供给，靠回调注入请求头。可以顺势讲"依赖方向"设计（第 20 章）。
  6. 状态归属纪律 —— Pinia 只放身份类状态、组织上下文放 URL、页面临时状态留页面、权威数据归后端。对照第 10 章口诀，讲"为什么不大包大揽做全局缓存"。
  7. 断点集中化的响应式架构 —— tokens.css 独占全部媒体查询，组件只消费变量；手机导航用 data 属性 + 变量切换，附带焦点管理。断点也是设计决策，改适配不用全局搜索。
  8. UI 工程化门禁 —— npm run check:ui 用脚本静态检查"有没有写死颜色/尺寸"，把设计规范变成可执行的规则，而非靠自觉。
最后一句话：答辩讲述的最佳结构是"问题 → 方案 → 效果"，而不是罗列技术名词。比如："多标签页和快速切换会带来迟到响应覆盖新数据的问题（问题），我们给每个请求登记会话代次，迟到的旧响应一律作废（方案），此后旧会话的响应无法污染新登录（效果）。"这个句式适用于上面每一条。

Q1 用两三分钟介绍一下这个项目（几乎必考的第一题）

参考答案（压缩成 STAR）：① 定位一句话：这是一个多组织活动管理系统——组织发布活动、成员认领任务、普通用户报名公开活动，还带经费管理与 AI 生成活动方案/总结草稿。② 我的角色：独立完成前后端，前端 Vue 3 + TypeScript（strict）+ Pinia + Element Plus，后端 Spring Boot + MySQL，共 19 张表。③ 主动抛两个技术点引导追问：全项目唯一的统一请求入口（错误分传输/业务两类）；多组织数据边界（当前组织存 URL、请求带序号与会话代次防竞态）。④ 收尾：有类型检查、ESLint、单元测试和 UI 规范门禁四项检查流水线，可随时验证。

可能追问："几个人做的？"——如实答独立完成，反而能接住后面所有深挖。"哪个模块最难？"——把话题引到 Q9 的竞态故事。

Q2 为什么选 Vue 而不是 React？为什么不用现成的后台模板？

参考答案：选型在《前端架构与技术栈设计》里论证过：单人毕设规模下，Vue 3 + Element Plus 中文生态成熟、学习曲线平缓、组件覆盖了表格表单弹窗等全部后台场景。同样重要的是"不选什么"：不引入 Tailwind、axios、额外状态库，标准能力（Fetch、URLSearchParams、AbortController、Intl）能解决就不加依赖——克制本身就是一种选型能力。不用现成 admin 模板，是因为权限边界和视觉规范需要精确可控，模板的黑盒布局反而难改。

可能追问："React 和 Vue 的差异？"——答响应式模型（Vue 的 Proxy 依赖追踪自动细粒度更新 vs React setState 触发重渲染再 diff）和心智模型（组合式函数 vs Hooks），别贬低任何一方。

Q3 登录是怎么实现的？凭证放哪里？怎么保证安全？

参考答案：表单编码 POST /api/auth/login（表单格式是开发规范定的），成功 204；会话凭证由后端通过 Set-Cookie 下发，前端 request() 统一带 credentials: 'same-origin'，JS 从不接触令牌本身。安全四件套：① CSRF——非 GET 请求自动附加防伪头，凭据由会话层"单飞"获取（并发只发一次，见 stores/session.ts）；② 401 统一处理——observeUnauthorized 里用会话代次保证"迟到的旧 401 不会把新登录清掉"；③ 登录回跳 safeNext() 只接受站内相对路径，防开放重定向钓鱼；④ 密码不进 URL、日志和任何持久存储。

可能追问："为什么不用 localStorage 存 JWT？"——localStorage 能被页面 JS 读取，一次 XSS 就能偷走令牌；Cookie 会话配合 CSRF 防伪（通常再加 HttpOnly、SameSite 属性）把两类攻击面分开处理。答出"两类攻击面"这个对比是加分点。

Q4 多组织切换，怎么保证 A 组织的数据不会串到 B 组织？

参考答案：分三层。① 单一真相：当前组织只存在 URL（/org/:orgId）里，Pinia 不保存可写的 currentOrgId，刷新、分享链接都不丢状态；架构文档明确禁止把"授权组织"写进服务端会话——那才是真正被多个标签页共享的地方。② 重建：切组织时 watch(orgId) 把页码、筛选、列表、角色等十来个状态逐一归零再重新请求（ActivitiesPage）。③ 竞态：每个在途请求带三重守卫——请求序号（防旧结果覆盖新结果）、目标 orgId（防旧组织数据渲染进新页面）、会话代次（防旧会话响应回填），守卫不满足直接丢弃响应（loadActivities）。

可能追问："为什么 URL 比 store 好？"——URL 天然可分享可刷新；store 里存第二份就成了两个真相。"后端还管吗？"——前端边界只是体验优化，每个请求后端都重新鉴权，安全底线在后端。

Q5 用户快速连点搜索或提交按钮，前端怎么处理？

参考答案：分场景。搜索：输入框的 query 和已生效的 appliedQuery 分离，点搜索才发请求，同时列表请求带序号，只接受最新一次的结果。提交：submitting 锁 + 按钮 :loading 在请求期间禁用——注意这不是防抖，第一次点击必须立刻生效；真正防的是副作用重复：写请求带幂等键（newIdempotencyKey()），网络中断重试时沿用同一个键，后端识别同一次意图不会重复创建。AI 生成这种"调一次模型有成本"的接口也用同样的幂等键（generateAiDraft）。

可能追问："防抖为什么不够？"——防抖只降低频率，不解决请求乱序和"结果未知时的重复副作用"，这两个要靠序号守卫和幂等键。

Q6 接口报错你们怎么统一处理？断网和"密码错误"是一回事吗？

参考答案：不是一回事，项目用 ApiError 的两个 kind 区分：transport（断网、超时、主动取消）统一提示"检查网络"；server（后端明确拒绝）带状态码、错误码、fieldErrors 字段级错误和 requestId，页面按业务含义给具体文案（如"账号或密码不正确"）。特殊码特殊处理：CSRF_INVALID 自动重取凭据提示重试；401 走全局会话清理。提交类接口还区分"明确失败"（400/403/422 等，可修改重填）和"结果未知"（超时/5xx，保留原内容和幂等键先去核对）。

可能追问："为什么 client 层不直接弹 toast？"——职责分层：传输层不做 UI 决策（架构文档明文规定），提示方式由页面自己定，否则全局错误会重复弹、乱弹。

Q7 为什么自己封装 ListPage？为什么共享组件只有这一个？

参考答案：所有列表页有同一条业务约束——面板状态必须互斥四态：失败（可重试）、首次加载（骨架屏）、空态、有数据（刷新保留旧内容只提示更新中）。用一个组件把状态机收敛（内部 computed 按"错误且无数据 → 骨架 → 空 → 就绪"归一），骨架屏还经过 leading/trailing 延迟防闪烁。扩展靠插槽（#actions/#filters/默认插槽/#empty 兜底内容），不靠 props 开关堆叠。共享组件只有它，是因为复用标准是"存在同一条业务约束或真的重复两处"，KPI 卡、AI 面板虽多处使用仍归各模块。还有一条真实教训可讲：页头样式曾提成全局类，导致工作台等其他页面构图被连带改掉，后来改回 scoped——全局样式是高危险品。

Q8 用户填了一半表单要离开，怎么处理？

参考答案：三道门对应三种离开方式：① 点关闭按钮——closeCreate() 先 ElMessageBox.confirm；② 点侧栏切路由——onBeforeRouteLeave/onBeforeRouteUpdate 路由守卫拦截确认；③ 直接关标签页——beforeunload 事件触发浏览器原生确认。判定"改过没"用脏检查快照：打开弹窗时 JSON.stringify(createForm) 存一份，之后实时比对。还有个细节：弹窗的"负责人候选人"列表请求在弹窗关闭或切组织时立即作废序号，旧响应不再回填。

Q9 这个项目里你遇到最难的技术问题是什么？（叙事题，务必准备）

参考叙事模板（问题→定位→解决→效果）：现象：切组织后偶现"新页面闪一下旧组织的活动列表"。定位：DevTools Network 面板发现是慢的旧请求晚到覆盖了新数据（竞态）；代码走查确认切页只发请求、没有作废旧状态。解决：三层方案——请求序号只认最新发起、会话代次作废跨会话响应、watch(orgId) 全量重建状态；并把规则固化进单测（session.spec.ts 有"迟到 401 不清掉新登录"这类用例）。效果：竞态类缺陷在后续迭代里没有再出现。备选叙事：幂等键设计（结果未知时的重复创建风险）、未保存三道门。避免说"踩坑无关痛痒的小 bug"。

Q10 前后端怎么联调？接口变更怎么保持同步？

可能追问："后端改了字段前端没跟上怎么办？"——类型检查对运行时差异无能为力，所以关键结构有运行时校验兜底 + 测试里 mock 响应体锁定形状。

Q11 AI 模块是怎么接入的？密钥和成本怎么管？

可能追问："为什么前端不直连厂商 API？"——密钥会暴露在浏览器、无法做组织级权限和用量控制，必须后端代理。"prompt 在哪拼？"——前端只传结构化业务条件（主题/目标/预算/时间地点等，空字段不下发），prompt 组装在后端，前端不维护提示词模板。

A · 前端核心基础

A1 说说你对事件循环（Event Loop）的理解

标准答案：JS 单线程，异步靠事件循环调度：执行完同步代码（调用栈清空）后，先清空全部微任务（Promise.then、queueMicrotask、MutationObserver），再取一个宏任务（setTimeout、事件回调、I/O）执行，如此往复；浏览器渲染插在宏任务之间。所以 await 后面的代码（微任务）先于 setTimeout 回调（宏任务）执行。

结合本项目：项目里真实出现的三处：① nextTick——创建活动弹窗打开后，等 Vue 把 DOM 更新完（微任务后）再 clearValidate() 清校验红字；② visibilitychange 的事件回调是宏任务，用来在切回标签页时重新验证会话；③ 所有 async/await 接口调用都是微任务链，理解它才能解释"为什么 loading 状态的恢复总在数据赋值之后"。

A2 说说浏览器的渲染流程/渲染管线

标准答案：解析 HTML 建 DOM 树、解析 CSS 建 CSSOM → 合成渲染树 → 布局（算几何位置）→ 绘制（填充像素）→ 合成（分层上屏）。JS 执行和样式计算会阻塞后续渲染；改几何属性触发重排（贵），只改颜色等触发重绘（较便宜）。

结合本项目：两个真实设计都服务这条管线：① 骨架屏与真实表格同构（行高、列宽来自同一批 token），加载完成切换时布局尺寸不变，几乎不产生布局偏移（CLS 指标好）；② 主题与断点全部走 CSS 变量——改一个 --ui-color-* 或断点变量，浏览器只做样式重算，DOM 结构不动，这是"换肤不卡顿"的结构性原因。

A3 你熟悉哪些 ES6+ 新特性？

标准答案：let/const 块级作用域、箭头函数、解构赋值、模板字符串、展开/剩余参数、默认参数、类与模块（import/export）、Promise 与 async/await、可选链 ?. 与空值合并 ??、Map/Set。

A4 Vue 的双向绑定和响应式原理（源码层面）

标准答案：双向绑定是 v-model 语法糖——原生元素上是 value + input 事件的合体，组件上是 modelValue + update:modelValue。响应式原理：Vue 3 用 Proxy 代理对象（对比 Vue 2 的 Object.defineProperty：解决了数组索引、新增/删除属性监听不到的问题），组件渲染时读到哪个属性就收集（track）哪个依赖，赋值时触发（trigger）这些依赖重新执行。

结合本项目：受控组件是手写的 v-model 协议：OrganizationSwitcher 接 modelValue prop、发 change 事件，自己不修改任何父级数据。追问"为什么 ref 要 .value"——Proxy 只能代理对象，单值需要一个引用容器，这就是 ref 的本质。

A5 说说你对 KeepAlive 的理解

标准答案：<KeepAlive> 缓存被切走的组件实例（含状态、DOM），配合 include/exclude/max 控制，激活/失活时触发 activated/deactivated 钩子；适合列表页 → 详情页 → 返回列表不丢滚动和筛选的场景。

结合本项目：项目没有用 KeepAlive，而且这是有理由的：多组织系统里，"回到列表"的正确状态取决于 URL（orgId、页码、筛选都在地址里），页面切换时由 watch(orgId) 从 URL 重建状态并校验数据有效性——用 KeepAlive 缓存反而要额外处理缓存失效和跨组织脏数据。知道什么时候不用一个技术，比会用它更能体现判断力。

A6 HTTP/1.1 → HTTP/2 → HTTP/3 有哪些改变？

标准答案：1.1：长连接复用 TCP，但同一连接上响应必须排队（应用层队头阻塞），文本头部冗余大。2：二进制分帧，一条连接上多个流（stream）并行交织，多路复用解决 HTTP 层队头阻塞；HPACK 压缩头部。3：底层从 TCP 换成 QUIC（基于 UDP），流之间独立丢包重传，解决 TCP 层队头阻塞；握手 0-RTT、连接迁移（切 Wi-Fi 不断）。

结合本项目：本地开发是 HTTP/1.1（Vite dev server + 代理）；生产按部署说明走 HTTPS。可以补一句理解：本项目所有页面路由级懒加载，产物是几十个小 chunk，HTTP/2 多路复用对"并行拉取小文件"的收益正明显——这就是为什么打包器都建议拆包而不是合一个大包。

A7 Webpack 的打包流程？Webpack 和 Vite 有哪些区别？

标准答案：Webpack：从 entry 出发递归构建依赖图，loader 转换非 JS 资源，plugin 在各阶段介入，最后打包成少数 bundle——开发冷启动需要全量构建，改一个文件也要重新走部分编译。Vite：开发期启动原生 ESM，按需编译——浏览器请求哪个模块才转译哪个，依赖用 esbuild 预构建（快一个数量级），HMR 精确到模块；生产构建用 Rollup。

结合本项目：项目用 Vite 7：strictPort 不漂移、/api 代理、路由全部动态 import() 与 ESM 天然契合，改一行保存毫秒级热更新（练习③验证过）。如实补充："生产打包我理解 Rollup 的 tree-shaking 和代码分割原理，但没有 Webpack 实战"——诚实比硬编好。

B · 前端结合 AI 的实际应用

B1 模型是怎么接入的？前端通常怎么接收流式数据？

标准答案：三种常见形态：后端代理 REST（一次性返回）、SSE 单向流（服务器持续推增量 token，打字机效果的主流方案）、WebSocket（双向，交互式场景）。前端接 SSE 用 EventSource，或需要 POST/自定义头时用 fetch + ReadableStream 读 reader 增量解析。

结合本项目：架构是后端代理：前端只调 /api/organizations/:id/ai/…，密钥永不下发浏览器（组织负责人配置一次，接口此后只返回"是否已配置"）。生成走"提交 → 生成记录状态 RUNNING/SUCCEEDED/FAILED"的异步模型，当前没有做流式；升级方案明确：生成接口改 SSE 后用 fetch 流式读取，AbortController 支持中途取消（项目的请求入口本来就有取消保护）。

B2 平时怎么写 prompt？或者怎么用 AI 写 prompt？

标准答案：结构化四要素：角色（你是活动策划顾问）、任务（生成活动方案草稿）、约束（预算内、输出格式、不得编造数据）、输出格式（章节结构/JSON schema）；复杂任务加 few-shot 示例；写完用固定评测集迭代，而不是凭感觉改。

结合本项目：项目把"prompt 的输入"字段化而不是拼长字符串：前端只提交结构化条件（主题/目标/受众/预算/时间地点/约束，空字段不下发，见 toPlanConditions），缺失项由模型标注"假设/待补充"；prompt 模板组装放在后端，前端不维护提示词文本——这样改提示词不用发版前端。

B3 渐进式加载是什么？打字机效果怎么实现？

标准答案：渐进式加载 = 不等全部数据，到一部分渲染一部分。流式打字机的实现要点：增量 append 而非整段重渲染、自动滚动到底部、光标动画、Markdown 内容按块缓冲（半行 Markdown 不渲染，攒到完整块再解析）、AbortController 支持停止生成、失败时保留已生成部分。

结合本项目：项目里"渐进"思想已经用在两处：列表四态（骨架 → 数据逐步上屏）和生成状态机（提交后立即展示 RUNNING 状态而不是白屏）。整段文本的打字机效果是明确的升级项（见第 28 章 Q12），方案就是 B1 说的 fetch 流式 + 增量渲染。

B4 怎么让大模型稳定输出 JSON？前端怎么解析与容错？

标准答案：服务端：开启 JSON mode / 结构化输出（传 JSON Schema 约束）、降低温度、prompt 里给 schema 和 few-shot、失败自动重试。前端容错四步：JSON.parse 包 try/catch；解析成功后逐字段运行时检查类型（字段缺失/类型不对不给过）；不合法时降级（展示原始文本让用户自行处理）；把失败上报而不是静默吞掉。

结合本项目："不信任运行时数据"正是项目的既有原则：后端错误结构 toProblemDetail 对 status/fieldErrors 逐字段确认类型才采用。AI 输出如果做结构化消费，会走同一套检查思路——可以把这句作为"我把通用 AI 工程问题和我的项目方法论接起来了"的证明。

B5 可以在哪些测试环节应用 AI 技术？

标准答案：测试用例初稿生成（给函数签名和业务规则让 AI 列边界）、mock 数据批量构造、单测样板代码、代码评审（找漏掉的空指针/竞态）、提交信息与文档生成。原则：AI 起草，人审核业务口径。

结合本项目：举真实例子：lifecycle.spec.ts 里"执行记录只在 EXECUTING/REVIEWING/CANCELLED 可写"这类状态机边界用例，很适合让 AI 按 7 个状态全遍历起草，人再核对业务口径；mock fetch 响应体（jsonResponse）也能批量生成。但像"会话代次防迟到 401"这种并发用例，必须人工设计——AI 容易漏掉时序前提。

C · 前端工程化与质量保障

C1 怎么判断一个 bug 是前端还是后端的？

标准答案（三段判定法）：打开 Network 面板看那次请求：① 请求根本没发出——前端逻辑问题（条件/事件没绑对）；② 发出了但参数错——前端组装问题；③ 参数正确但响应数据错——后端问题；④ 响应正确但页面显示错——前端渲染问题。状态码速记：4xx 看请求、5xx 找后端、请求是 200 但业务失败看响应体错误码。

结合本项目：第 21 章的三个实战配方就是这套方法：登录跳转异常先查 /api/auth/me 是 200 还是 401；列表数据不对先看 Payload 再看 Response，一步分清"前端没发对"还是"后端没给对"。项目错误响应统一带 requestId，报障时把请求号给后端可直接定位日志。

C2 你一般怎么设计测试用例？从哪些角度去测？

标准答案：方法上：等价类划分 + 边界值分析 + 场景法（用户旅程）；角度上：功能、兼容性（浏览器/移动端）、交互（加载/空态/错误）、弱网、安全、无障碍。

结合本项目（全是真实例子）：边界值——活动状态机用 7 个状态全枚举遍历断言可写状态；金额校验正则限定两位小数的边界；结束时间必须晚于开始时间。兼容性——pointer: coarse 媒体查询下控件高度提到触控标准。弱网——DevTools Slow 3G 验证四态不闪跳。无障碍——role="alert" 错误播报、抽屉关闭后焦点还给菜单按钮、prefers-reduced-motion 全量降级动画。安全——CSRF 头、权限以后端为准、密码不落盘。

C3 冒烟测试和回归测试的区别？一套完整测试由哪些阶段组成？

标准答案：冒烟 = 每个版本先跑主链路（登录 → 建组织 → 建活动），通过才值得深入测；回归 = 改动之后重跑相关用例和核心用例，防止"修好 A 弄坏 B"。阶段：单元 → 组件/集成 → 接口 → 系统（E2E）→ 验收。

结合本项目：项目把回归做成了自动化流水线：npm run test -- --run（业务规则单测）+ typecheck + lint + check:ui（设计规范门禁），任何改动四项全绿才算过；冒烟对应人工走"注册→登录→建组织→创建活动"主链路。E2E 尚未引入，规划中（诚实 + 有理由：跨组织权限与金额一致性由后端数据库测试证明）。

C4 你会关注接口并发问题吗？并发会导致什么？怎么测？

标准答案：会。典型问题：重复点击造成重复提交（重复下单/重复建单）、响应乱序旧数据覆盖新数据、会话切换时旧请求污染新会话。测试手段：弱网 + 快速连续操作、DevTools 限速、自动化时序用例（mock 慢响应）。

结合本项目（这是项目最强的一题，放开讲）：五层防线各有真实代码：① 防重复触发——submitting 锁 + 按钮 loading；② 防重复副作用——幂等键 Idempotency-Key，AI 生成同键重放不重复调模型；③ 防乱序——请求序号 requestSeq；④ 防跨会话污染——会话代次 generation，迟到的旧 401/响应作废；⑤ 防切页竞态——orgId 守卫 + watch(orgId) 重建。而且有测试固化：session.spec.ts 专门验证"迟到的 401 不清掉新登录"。

C5 性能测试怎么做？FCP/LCP 这些指标了解吗？

标准答案：核心指标：FCP（首次内容绘制）、LCP（最大内容绘制，核心体验指标，建议 <2.5s）、CLS（累积布局偏移）、INP（交互响应性）。工具：Lighthouse（跑分+建议）、Performance 面板（录制分析主线程）、Network 面板看资源瀑布。优化抓手：减小首包 JS、关键资源优先、避免布局抖动、图片懒加载。

结合本项目：已做的优化可以对应指标讲：路由级懒加载让首屏只下载登录页代码（直接减小 FCP/LCP 前的下载量）；骨架屏同构设计控制 CLS；Element Plus 按需显式引入避免全量样式。如实说明：项目尚未建立正式的性能基线测量流程，这是我列的迭代项之一——知道指标和抓手，缺的是数据化验收。

C6 灰度发布后仍有问题怎么办？前端的灰度和回滚机制？

标准答案：前端灰度通常按用户/流量百分比把入口指向新版本（静态资源按内容 hash 版本化，index.html 不缓存、chunk 长缓存），出问题把入口切回旧版本即回滚——前提是接口向后兼容、新旧前端能共存。配合前端错误监控（上报 JS 异常 + requestId）尽早发现。

结合本项目：项目未上线，没有灰度实操，可如实说思路 + 已具备的基础：构建产物带 hash、深链接与只读代理已验证（部署说明），回滚的基础设施是齐的，缺的是发布平台与监控告警——把"没做过"转化为"知道缺什么"。
